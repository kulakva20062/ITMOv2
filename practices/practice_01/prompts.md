## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: Провести ревью предоставленного диффа PR и найти проблемы с чёткими evidence и проверками.
- Роль AI: AI-ревьюер PR и технический писатель, формирующий контекст, проблему, промпт и обзор рисков.

### 2. Входы и источники

- Обязательный вход: Файл `practices/practice_01/TRAINING_PR.diff` (unified diff).
- Разрешённые файлы и источники: Только указанный diff; без внешних правил репозитория.
- Context Pack — факты, правила, примеры и ограничения: см. `context.md` (разделы «Факты и правила», «Формат входа и результата», «Ограничения...»).

### 3. Задача и артефакты

- Что сделать: Проанализировать дифф, составить список рисков с evidence и проверками; обновить `context.md`, `problem.md`, `prompts.md` согласно требованиям практики.
- Что вернуть: Ревью (summary + ≤3 риска с evidence и check), обновлённые файлы контекста, проблемы и промптов.

### 4. Формат результата

- Структура ответа: 
  1) Summary (2–4 предложения). 
  2) Риски (до 3), каждый: file:line + evidence (цитата) + почему риск + check. 
  3) Если нарушений нет — пустой список рисков.
- Ограничения объёма: Кратко, без лишних деталей; использовать цитаты ровно для evidence.

### 5. Полномочия и запреты

- Разрешено: Править только `context.md`, `problem.md`, `prompts.md`; использовать факты из диффа.
- Запрещено: Апрувить/мержить; придумывать правила/ID; менять код в `app/`; править раздел «P1-01 Findings».

### 6. Рабочий процесс и остановка

- Шаги: 
  1) Прочитать diff. 
  2) Обновить context/problem/prompts. 
  3) Сформировать риски с evidence. 
  4) Составить проверки. 
  5) Сверить границы полномочий.
- Когда остановиться и запросить человека: При противоречиях в диффе или необходимости внешних правил/требований.

### 7. Проверки и evidence

- Как проверять утверждения: Каждое утверждение подтверждать ссылкой на строки диффа с цитатой; проверки должны быть воспроизводимыми на основе кода.
- Какое evidence сохранить: file:line и точная цитата из `TRAINING_PR.diff` для каждого риска.

### 8. Definition of Done

- Задача закончена, когда: Заполнены `context.md`, `problem.md`, `prompts.md` без плейсхолдеров; у каждого риска есть evidence и check; границы соблюдены; раздел P1-01 не изменён.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Частично | Полностью (file:line для каждого риска) | Разница не в наличии ссылки, а в её проверяемости. Zero-shot назвал файлы верно, но приписал им номера строк `+35–38` и `+19–22`, которых в диффе нет: оба файла начинаются со строки 1, хунки — `@@ -1,8 +1,17 @@` и `@@ -1,10 +1,23 @@`. Master prompt потребовал брать номера из заголовков хунков и указывать диапазон, если точная строка неизвестна, — ссылки стали воспроизводимыми, а не правдоподобными |
| Вывод подтверждён diff или правилом | Да, только diff | Да, только diff | Формально в обоих запусках источником был дифф, но zero-shot без правил репозитория оценивал код по общим представлениям о «хорошем API»: отсюда prompt injection, Python 3.8, ретраи и rate limiting — пункты, которые нечем подтвердить. С Context Pack у каждого вывода появился адрес: SEC-1, API-1, REL-1, OUT-1, OBS-1. Правила ещё и задали числа — 20 000 символов, 10 секунд, не более трёх рисков, — которых zero-shot придумать не мог и потому писал «ограничить размер» без величины |
| Соблюдены границы AI | Частично | Полностью | Zero-shot вышел за рамки советующей роли: раздел «Рекомендованные первичные изменения» — это план правок в `app/`, то есть предложение писать код. Master prompt зафиксировал SCOPE-1 и запрет менять `app/`, поэтому третий запуск дал документацию и проверки, а решение и приёмку явно оставил человеку (колонки в `project_management.md`, «Ответственные» в `adr.md`) |
| Есть воспроизводимая проверка | Частично | Полностью | У zero-shot проверки сформулированы как намерения: «проверить большие diff», «добавить тесты». Master prompt задал форму проверки — конкретный вход и наблюдаемый критерий, — и это перевело их в исполнимый вид: тело `{}` → 422 и ноль вызовов заглушки, дифф в 20 001 символ → 413, заглушка, отвечающая 11 секунд → 503 не позже 11 с, маркер `MARKER_SECRET_VALUE_42` отсутствует в логе. Побочный эффект: тесты стали распределяться по уровням, потому что критерий «что наблюдаем» отличает unit от e2e |

## P1-01 Findings

Ниже — найденные проблемы в диффе `TRAINING_PR.diff` (см. файл), упорядочены по важности, с отсылками к изменениям.

- Высокая важность
  - app/api.py +35–38: Отсутствует валидация входа. Используется `payload: dict` и прямой доступ `payload["diff"]`. При отсутствии ключа будет 500. Нужна Pydantic‑модель или явная проверка и возврат 400/422.
  - app/review_service.py +19–22: Нет обработки ошибок и таймаутов LLM. Любая ошибка приведёт к 500. Нужны try/except, таймауты, перевод ошибок в предсказуемые коды.
  - app/review_service.py +19–22: Неограниченный размер входа в LLM. Риск переполнения контекста и затрат. Ограничить/резюмировать/батчить diff.
  - app/api.py +35–38: Неструктурированный ответ `{"comment": str}`. Лучше возвращать список findings с полями: файл, диапазон строк/хунк, серьёзность, сообщение.
  - app/api.py +35–38: Синхронный маршрут вызывает потенциально I/O‑блокирующий LLM. Рассмотреть async/фоновые задачи/пулы.
  - Безопасность: POST /api/reviews без аутентификации/лимитов -> риск злоупотреблений/DoS. Добавить auth, rate limiting, ограничения размера/времени.

- Средняя важность
  - app/api.py +35–38: Нет явной модели ответа — OpenAPI будет нечётким. Использовать Pydantic‑модель.
  - app/review_service.py +19–22: Риск prompt injection из содержимого diff. Добавить строгие инструкции, делимитеры, пост‑валидацию.
  - Тесты: отсутствуют. Проверить успешный путь, ошибки валидации, большие diff, ошибки LLM, формат ответа.
  - Статусы ответов: для создания — 201; для ошибок — чёткие 4xx/5xx.
  - Логирование/метрики: нет.

- Низкая важность
  - Типизация: `dict[str, str]` требует Python 3.9+. Если целевая 3.8 — использовать `Dict`.
  - app/review_service.py +10–13: Стиль `Protocol.generate` — косметика.
  - API‑дизайн: согласовать путь `/api/reviews` с принятой схемой.

- Открытые вопросы
  1. Какая минимальная версия Python?
  2. Нужна ли структурированная схема findings?
  3. Требуется ли аутентификация/квоты?
  4. Ограничения по размеру диффа/таймауты?

- Рекомендованные первичные изменения
  1. Pydantic‑модели запроса/ответа и валидация `diff`.
  2. Ограничение размера входа, таймауты и обработка ошибок LLM.
  3. Структурированный результат (список findings).
  4. Базовая защита: auth/лимиты/ограничения размера.
  5. Тесты на нормальные и ошибочные сценарии.
