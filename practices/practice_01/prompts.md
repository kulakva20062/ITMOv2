## Master Prompt v1

Инструкция запуска P1-03 целиком хранится в `practices/practice_01/Promt/P1-03_master_prompt.txt`. Ниже — её изложение по восьми разделам.

### 1. Цель и роль

- Цель: по одному учебному диффу собрать связный каркас SDLC-артефактов для одного сквозного сценария `POST /api/reviews`, где каждое утверждение подтверждено строкой диффа или правилом репозитория.
- Роль AI: инженер-аналитик, ведущий документацию продукта и отвечающий за её проверяемость; кода не пишет и решения по PR не принимает.

### 2. Входы и источники

- Обязательный вход: `practices/practice_01/TRAINING_PR.diff` — unified diff из двух файлов, единственный источник фактов о коде.
- Разрешённые файлы и источники: файлы каталога `practices/practice_01/` (правка — только их) и текст самой инструкции запуска; внешних источников нет.
- Context Pack — факты, правила, примеры и ограничения: факты о коде — хунк `app/review_service.py @@ -1,10 +1,23 @@` (`class LLM(Protocol)` с `def generate(self, prompt: str) -> str`, метод `def review(self, diff: str) -> dict[str, str]`, `prompt = f"Review this pull request and find problems:\n{diff}"`, `answer = self.llm.generate(prompt)`, `return {"comment": answer}`) и хунк `app/api.py @@ -1,8 +1,17 @@` (`@app.post("/api/reviews")`, `def create_review(payload: dict) -> dict[str, str]:`, `return review_service.review(payload["diff"])`, уже существовавший `@app.get("/health")`). Вывод об отсутствии: в этих хунках нет строк валидации тела, ограничения длины диффа, маскирования секретов, таймаута, `try/except` и логирования. Правила репозитория заданы самой инструкцией запуска и только ею, ссылаться на внешний файл правил запрещено: SEC-1 — перед отправкой во внешний LLM из диффа удаляются токены, пароли, приватные ключи; API-1 — дифф длиннее 20 000 символов отклоняется с HTTP 413; REL-1 — LLM-вызов имеет timeout 10 секунд, ошибка превращается в контролируемый ответ; OUT-1 — ответ содержит `summary`, массив `risks` и массив `checks`, в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`; SCOPE-1 — сервис только советует, решение по PR принимает человек; QA-1 — утверждение включается, только если подтверждено строкой диффа или правилом; OBS-1 — в лог пишутся только `request_id`, длительность и статус, дифф и ответ модели не логируются. Формат входа: `POST /api/reviews`, `Content-Type: application/json`, тело `{"diff": "<unified diff>"}`; результат сейчас — `{"comment": "<строка ответа LLM>"}`, целевой по OUT-1 — `{"summary": "...", "risks": [...], "checks": [...]}`.

### 3. Задача и артефакты

- Что сделать: заполнить одиннадцать файлов в `practices/practice_01/` — context.md, problem.md, analysis.md, product_management.md, project_management.md, adr.md, tests_unit.md, tests_integration.md, tests_load.md, tests_e2e.md, prompts.md, сохранив заголовки шаблонов и обязательные якоря (`## Context Pack`, `## Метрики`, `## TO BE`, блок gherkin, блок mermaid, `## Архитектурная схема`).
- Что вернуть: одиннадцать заполненных файлов, описывающих ОДИН сквозной сценарий `POST /api/reviews`, каждый — с разделом «Как использовали AI» со ссылкой на строку P1-03 в этом файле.

### 4. Формат результата

- Структура ответа: русский язык, деловой стиль, без маркетинговых оборотов; ссылка на код — только заголовком хунка (`app/api.py @@ -1,8 +1,17 @@`), потому что оба файла в диффе начинаются со строки 1, выдуманных номеров строк быть не должно; ссылка на правило — по ID.
- Ограничения объёма: таблицы заполняются целиком, пустых ячеек и плейсхолдеров не остаётся; числа приводятся только заданные правилами (20 000 символов, 10 секунд, три элемента в `risks`) либо явно помеченные как допущение с условием замены.

### 5. Полномочия и запреты

- Разрешено: править только файлы в `practices/practice_01/`.
- Запрещено: менять код в `app/` и сам `TRAINING_PR.diff`; approve или merge PR (SCOPE-1); ссылаться на внешний файл правил — правила берутся из самой инструкции запуска; придумывать новые ID правил; изменять раздел «P1-01 Findings» и строки P1-01 и P1-02 в этом файле; вписывать оценку студента и результаты запусков, которых не было.

### 6. Рабочий процесс и остановка

- Шаги: прочитать `TRAINING_PR.diff` целиком → заполнить context.md и problem.md → заполнить analysis.md, product_management.md, project_management.md → заполнить adr.md → заполнить четыре файла тестов, разведя уровни ответственности → заполнить строку P1-03 в этом файле → прогнать `make test` из корня репозитория.
- Когда остановиться и запросить человека: при противоречии между источниками и при необходимости требования, которого нет ни в диффе, ни в перечне правил; разрешать такое противоречие самостоятельно нельзя (SCOPE-1).

### 7. Проверки и подтверждения

- Как проверять утверждения: каждый риск и каждое требование сопровождается evidence — цитатой из хунка или ID правила, неподтверждённое не включается (QA-1); каждая проверка формулируется как конкретный вход и наблюдаемый критерий, а не как намерение («добавить тесты» недопустимо); уровни тестов разводятся по наблюдаемому критерию — unit на перехваченном аргументе, integration на стыке компонентов, load по времени и доле отказов под потоком, e2e по коду ответа клиенту; метрики не содержат финансовых и опросных показателей.
- Какие результаты проверки сохранить: строку P1-03 в таблице выше (что принято, что отклонено, как проверено), таблицу сравнения двух запусков ниже и вывод `make test`.

### 8. Definition of Done

- Задача закончена, когда: одиннадцать файлов заполнены без плейсхолдеров и `make test` проходит; у каждого утверждения есть evidence — хунк или ID правила; нет ни одной ссылки на внешний файл правил, все правила названы по ID; раздел «P1-01 Findings» и строки P1-01, P1-02 не изменены; все одиннадцать файлов описывают один и тот же сценарий, а ссылки между ними указывают на существующие разделы.

## P1-01 Findings

Ниже — найденные проблемы в диффе `TRAINING_PR.diff` (см. файл), упорядочены по важности, с отсылками к изменениям.

- Высокая важность
  - app/api.py +35–38: Отсутствует валидация входа. Используется `payload: dict` и прямой доступ `payload["diff"]`. При отсутствии ключа будет 500. Нужна Pydantic‑модель или явная проверка и возврат 400/422.
  - app/review_service.py +19–22: Нет обработки ошибок и таймаутов LLM. Любая ошибка приведёт к 500. Нужны try/except, таймауты, перевод ошибок в предсказуемые коды.
  - app/review_service.py +19–22: Неограниченный размер входа в LLM. Риск переполнения контекста и затрат. Ограничить/резюмировать/батчить diff.
  - app/api.py +35–38: Неструктурированный ответ `{"comment": str}`. Лучше возвращать список findings с полями: файл, диапазон строк/хунк, серьёзность, сообщение.
  - app/api.py +35–38: Синхронный маршрут вызывает потенциально I/O‑блокирующий LLM. Рассмотреть async/фоновые задачи/пулы.
  - Безопасность: POST /api/reviews без аутентификации/лимитов -> риск злоупотреблений/DoS. Добавить auth, rate limiting, ограничения размера/времени.

- Средняя важность
  - app/api.py +35–38: Нет явной модели ответа — OpenAPI будет нечётким. Использовать Pydantic‑модель.
  - app/review_service.py +19–22: Риск prompt injection из содержимого diff. Добавить строгие инструкции, делимитеры, пост‑валидацию.
  - Тесты: отсутствуют. Проверить успешный путь, ошибки валидации, большие diff, ошибки LLM, формат ответа.
  - Статусы ответов: для создания — 201; для ошибок — чёткие 4xx/5xx.
  - Логирование/метрики: нет.

- Низкая важность
  - Типизация: `dict[str, str]` требует Python 3.9+. Если целевая 3.8 — использовать `Dict`.
  - app/review_service.py +10–13: Стиль `Protocol.generate` — косметика.
  - API‑дизайн: согласовать путь `/api/reviews` с принятой схемой.

- Открытые вопросы

  3. Требуется ли аутентификация/квоты?
  4. Ограничения по размеру диффа/таймауты?

- Рекомендованные первичные изменения
  1. Pydantic‑модели запроса/ответа и валидация `diff`.
  2. Ограничение размера входа, таймауты и обработка ошибок LLM.
  3. Структурированный результат (список findings).
  4. Базовая защита: auth/лимиты/ограничения размера.
  5. Тесты на нормальные и ошибочные сценарии.
