# Проблема и метрики

Сценарий — `POST /api/reviews`. Факты берутся из хунков `app/api.py @@ -1,8 +1,17 @@` и `app/review_service.py @@ -1,10 +1,23 @@` файла `TRAINING_PR.diff`, правила — по ID (перечень и формулировки: [`context.md`](context.md), раздел «Факты и правила»).

## Проблема

- Пользователь: автор PR или ревьюер, который отправляет unified diff на `POST /api/reviews` и ожидает пригодный к работе разбор. Решение по самому PR принимает человек (SCOPE-1 — сервис только советует, не пишет код и не действует в GitHub).
- Ситуация: клиент шлёт `{"diff": "<unified diff>"}` и получает `{"comment": "<строка ответа LLM>"}` — факт из хунка `app/review_service.py @@ -1,10 +1,23 @@`, строка `return {"comment": answer}`.
- Что происходит сейчас:
  - тело без ключа `diff` роняет обработчик: `return review_service.review(payload["diff"])` (`app/api.py @@ -1,8 +1,17 @@`) — обращение по ключу без проверки, на теле `{}` возникает `KeyError`, потому что аннотация `payload: dict` не описывает состав тела;
  - дифф уходит во внешнюю модель дословно: `prompt = f"Review this pull request and find problems:\n{diff}"` — нарушение SEC-1 (перед отправкой во внешний LLM из диффа удаляются токены, пароли, приватные ключи), так как строк маскирования в хунке нет;
  - длина диффа нигде не проверяется — вывод об отсутствии: ни в одном из двух хунков нет строки, сравнивающей размер входа с порогом, поэтому API-1 (дифф длиннее 20 000 символов отклоняется с HTTP 413) не соблюдается;
  - `answer = self.llm.generate(prompt)` вызывается без таймаута и без `try/except` — нарушение REL-1 (LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ); при этом обработчик синхронный (`def create_review(payload: dict) -> dict[str, str]`), поэтому ожидание модели удерживает рабочий поток;
  - ответ — одна строка вместо структуры: `{"comment": answer}` не содержит `summary`, `risks`, `checks` — нарушение OUT-1 (в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`);
  - соблюдение OBS-1 (в лог пишутся только `request_id`, длительность и статус; дифф и ответ модели не логируются) подтвердить нечем: вывод об отсутствии — ни одной строки логирования в обоих хунках, то есть нет ни `request_id`, ни длительности, ни статуса.
- Почему это мешает пользователю или бизнесу: пользователь не может отличить отказ валидации от сбоя модели — оба приходят как необработанная ошибка (нет `try/except`, REL-1); ответ `{"comment": "<строка>"}` нельзя разложить по файлам и рискам, поэтому его приходится перечитывать вручную вместо работы по `risks` (OUT-1); дословная подстановка диффа выносит содержимое репозитория во внешнюю модель без удаления секретов (SEC-1); отсутствие проверки длины оставляет приём произвольно больших тел (API-1); отсутствие логов не даёт разобрать ни один инцидент постфактум (OBS-1).
- Что не входит в задачу: изменение кода в `app/` и самого `TRAINING_PR.diff` (артефакты только описывают сценарий); approve или merge PR (SCOPE-1); выбор провайдера LLM и его тарифов — ни одна строка хунков его не называет; аутентификация и квоты — такого правила среди SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1 нет, а строк диффа о них тоже нет (QA-1).

## Почему изменение метрики подтвердит решение проблемы

Каждая метрика закрывает ровно одно из перечисленных выше наблюдений и измеряется тем же входом, которым это наблюдение обнаружено.

- Первая и вторая метрики адресуют вход: пока `payload["diff"]` берётся без проверки, тело `{}` даёт `KeyError`; переход этой доли к 100% означает, что на том же теле `{}` наблюдается код ответа, а не падение. То же для API-1: единственный способ отличить соблюдение от несоблюдения — подать 20 001 символ и увидеть 413.
- Третья метрика проверяема без доступа к внешней модели: наблюдаемый объект — перехваченный аргумент `prompt` заглушки. Если в нём не осталось секретов, требование SEC-1 выполнено именно на той строке, где дифф подставляется в промпт.
- Четвёртая метрика подтверждает REL-1 по наблюдаемому поведению: заглушка задерживает ответ дольше 10 секунд, и вместо зависания клиент получает контролируемый ответ. Это же снимает эффект синхронного обработчика `def create_review`, потому что ожидание ограничено сверху.
- Пятая метрика фиксирует переход от `{"comment": answer}` к форме OUT-1 и одновременно проверяет ограничение в три элемента `risks` — без него структура формально есть, а требование не выполнено.
- Шестая метрика — единственный способ подтвердить OBS-1: сейчас логов нет вовсе, поэтому соблюдение или нарушение правила ненаблюдаемо. Наличие `request_id`, длительности и статуса при отсутствии диффа и ответа модели делает правило проверяемым.

Метрики, которые сознательно не взяты: стоимость запроса и экономия времени ревьюера (финансовые показатели), удовлетворённость пользователей (опросный показатель) — ни один из них не привязан ни к одной строке хунков и ни к одному из ID правил, поэтому по QA-1 они не включены.

## Как использовали AI

- Для чего: сформулировать проблему одного сценария `POST /api/reviews` и подобрать метрики, каждая из которых измеряется наблюдаемым входом и подтверждена строкой хунка или ID правила.
- Тип промпта: master prompt.
- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверил студент и какие исправления поручил агенту: сверил формулировки с хунками — `payload["diff"]`, `prompt = f"Review this pull request and find problems:\n{diff}"`, `answer = self.llm.generate(prompt)`, `return {"comment": answer}` процитированы дословно. Поручил убрать из таблицы метрику стоимости запроса и метрику удовлетворённости ревьюеров: обе не привязаны ни к одной строке диффа (QA-1). Поручил заменить формулировку «уменьшить число ошибок» на конкретную долю с указанием входа, на котором она измеряется. Проверил, что отсутствие проверки длины, таймаута и логирования описано как вывод об отсутствии, а не как цитата.
