## Context Pack

Отобранное для одной задачи: сквозной сценарий «клиент отправляет `POST /api/reviews` с диффом → сервис возвращает структурированное ревью по OUT-1 → человек принимает решение».

### Факты из диффа

- `app/api.py` (`@@ -1,8 +1,17 @@`): добавлен маршрут и обработчик —
  `@app.post("/api/reviews")`, `def create_review(payload: dict) -> dict[str, str]:`,
  `return review_service.review(payload["diff"])`.
- `app/api.py` (`@@ -1,8 +1,17 @@`): `@app.get("/health")` присутствует в контексте хунка без изменений.
- `app/review_service.py` (`@@ -1,10 +1,23 @@`): добавлен метод —

  `return {"comment": answer}`.
- `app/review_service.py` (`@@ -1,10 +1,23 @@`): сигнатура протокола `def generate(self, prompt: str) -> str` переоформлена с однострочной записи на многострочную. Поведение не меняется, риском не является.
- Выводы об отсутствии (доказываются отсутствием строк в приведённых хунках, это не цитата): в диффе нет валидации тела запроса, ограничения длины диффа, удаления секретов, таймаута, обработки ошибок LLM, логирования, аутентификации и тестов.

### Правила, влияющие на этот PR

| ID | Правило | Связь с диффом |
|---|---|---|
| SEC-1 | Перед отправкой во внешний LLM из диффа удаляются токены, пароли, приватные ключи | `review()` подставляет `diff` в f-строку промпта как есть |
| API-1 | Дифф длиннее 20 000 символов отклоняется с HTTP 413 | Проверки длины нет ни в маршруте, ни в сервисе |
| REL-1 | LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ | `self.llm.generate(prompt)` вызывается без таймаута и без `try/except` |
| OUT-1 | Ответ содержит `summary`, массив `risks` и массив `checks`; в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk` | Сервис возвращает `{"comment": answer}` — одну строку |
| SCOPE-1 | Сервис только советует: не пишет код и не действует в GitHub | Граница продукта; решение по PR остаётся за человеком |
| QA-1 | Риск включается, только если подтверждён строкой диффа или правилом | Критерий отбора рисков и тестов во всех артефактах |
| OBS-1 | В лог пишутся только `request_id`, длительность и статус; дифф и ответ модели не логируются | Логирования в диффе нет вообще — правило задаёт, каким оно должно быть |

### Формат входа и результата

- Вход: `POST /api/reviews`, `Content-Type: application/json`, тело `{"diff": "<unified diff>"}`.
- Результат сейчас (факт из диффа): `{"comment": "<строка ответа LLM>"}`.
- Результат целевой (правило OUT-1): `{"summary": "<строка>", "risks": [{"file": "...", "line": "...", "evidence": "...", "risk": "..."}], "checks": ["..."]}`, где `risks` — не более трёх элементов.

### Ограничения и запрещённые действия

- Единственный источник фактов о коде — `TRAINING_PR.diff`; правила берутся по ID из `CASE.md`.
- Код в `app/` в рамках практики не меняется: артефакт работы — документация (SCOPE-1).
- Помощник не делает approve, merge и не изменяет содержимое PR (SCOPE-1).
- Риск или проверка без evidence не включается (QA-1).
- Номера строк берутся из заголовков хунков; при неизвестной точной строке указывается диапазон хунка.

### Хороший пример комментария

```text
app/review_service.py (хунк @@ -1,10 +1,23 @@) — строка
prompt = f"Review this pull request and find problems:\n{diff}"
отправляет дифф во внешний LLM без удаления секретов, что нарушает SEC-1.
Проверка: передать дифф со строкой "AWS_SECRET_ACCESS_KEY=AKIA..." и убедиться,
что в собранном prompt вместо значения стоит [REDACTED].
```

### Плохой пример комментария

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

Почему плохой: нет файла и строки, нет ссылки на правило, нет воспроизводимой проверки — такой риск отбрасывается по QA-1.

### Что пока неизвестно

- Реальный состав команды и роли — в четырёх источниках нет; в плане поставки помечено как допущение.
- Измеренные значения метрик: ни одного замера не проводилось, в `problem.md` указан способ замера, а не число.
- Провайдер LLM за протоколом `LLM` и его собственные лимиты — дифф показывает только протокол `generate(self, prompt: str) -> str`.
- Нужны ли аутентификация и квоты для `/api/reviews` — ни одно из семи применимых правил этого не задаёт, в диффе аутентификации нет.
- Формат `line` в OUT-1 (номер строки или диапазон хунка) — `CASE.md` задаёт только имя поля.
- Коды ответа для случаев, которые правила не покрывают: правилами задан только 413 (API-1). Коды 422, 502 и 503 выбраны как проектное решение и зафиксированы в [`adr.md`](adr.md) — при появлении внешнего требования их нужно пересмотреть.

## Как использовали AI

- Для чего: собрать AS IS и Context Pack по одному сквозному сценарию, отделив факты диффа от выводов об отсутствии и от допущений.
- Тип промпта: master prompt (третий запуск, P1-03); baseline — zero-shot P1-01 и master prompt v1 P1-02.
- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: перечитали `TRAINING_PR.diff` и заменили унаследованные из P1-01 номера строк `app/api.py +35–38` и `app/review_service.py +19–22` на диапазоны хунков `@@ -1,8 +1,17 @@` и `@@ -1,10 +1,23 @@` — файлы в диффе начинаются со строки 1, поэтому строки 35–38 в них существовать не могут. Отбросили как недоказуемые тезисы P1-01 про prompt injection, версию Python 3.8 и rate limiting: ни строки диффа, ни правила из `CASE.md` их не подтверждают. Два правила `CASE.md`, прямо помеченные там как не относящиеся к учебному PR, в Context Pack не переносились: они не связаны ни с одной строкой этого диффа. Отдельно отмечаю расхождение, которое ревьюер увидит при чтении подряд: раздел «Master Prompt v1» в [`prompts.md`](prompts.md) ссылается на прежние названия разделов этого файла — «Факты и правила» с тех пор разделены на «Факты из диффа» и «Правила, влияющие на этот PR», а заголовок Context Pack сокращён до вида, который проверяет `make test`. Тот раздел — зафиксированная история второго запуска, править его нельзя, поэтому соответствие указано здесь, а не там.
