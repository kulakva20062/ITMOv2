# Master Prompt P1-03 — заполнение одиннадцати артефактов Практики 1

## 1. Цель и роль

Цель: по одному учебному диффу собрать связный каркас SDLC-артефактов для
одного сквозного сценария `POST /api/reviews`, где каждое утверждение
подтверждено строкой диффа или правилом из раздела 2.4 этого промпта.

Роль: инженер-аналитик, который ведёт документацию продукта и отвечает
за её проверяемость. Ты не пишешь код и не принимаешь решение по PR.

`practices/practice_01/TRAINING_PR.diff` — unified diff из двух файлов.
Это единственный источник фактов о коде.

### 2.3. Выводы об отсутствии

В приведённых хунках НЕТ строк валидации тела, ограничения длины диффа,
маскирования секретов, таймаута, `try/except` и логирования. Это вывод
об отсутствии, а не цитата: так и формулируй его в артефактах.

### 2.4. Правила репозитория (Context Pack)

Правила заданы здесь и только здесь. Ссылаться на внешний файл правил
запрещено: в репозитории такого файла нет, и ссылка на него была бы
невоспроизводимой. В артефактах ссылайся на правило по его ID, а при
первом употреблении в файле приводи формулировку.

| ID | Правило |
|---|---|
| SEC-1 | Перед отправкой во внешний LLM из диффа удаляются токены, пароли, приватные ключи |
| API-1 | Дифф длиннее 20 000 символов отклоняется с HTTP 413 |
| REL-1 | LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ |
| OUT-1 | Ответ содержит `summary`, массив `risks` и массив `checks`; в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk` |
| SCOPE-1 | Сервис только советует: не пишет код и не действует в GitHub, решение по PR принимает человек |
| QA-1 | Утверждение включается, только если подтверждено строкой диффа или правилом |
| OBS-1 | В лог пишутся только `request_id`, длительность и статус; дифф и ответ модели не логируются |

### 2.5. Формат входа и результата

Вход: `POST /api/reviews`, `Content-Type: application/json`,
тело `{"diff": "<unified diff>"}`.
Результат сейчас (факт из диффа): `{"comment": "<строка ответа LLM>"}`.
Результат целевой (по OUT-1): `{"summary": "...", "risks": [...], "checks": [...]}`.

Заполни одиннадцать файлов в `practices/practice_01/`, сохранив

Все артефакты описывают ОДИН сквозной сценарий `POST /api/reviews`.
Каждый файл содержит раздел «Как использовали AI» со ссылкой на строку
P1-03 в `prompts.md`.

## 4. Формат результата

- Русский язык, деловой стиль, без маркетинговых оборотов.
- Ссылка на код — только через заголовок хунка
  (`app/api.py @@ -1,8 +1,17 @@`), потому что оба файла в диффе
  начинаются со строки 1; выдуманных номеров строк быть не должно.
- Ссылка на правило — по ID из таблицы 2.4.
- Таблицы заполняются целиком: пустых ячеек и плейсхолдеров не остаётся.
- Числа приводятся только те, что заданы правилами (20 000, 10 секунд,
  три элемента в `risks`) либо явно помечены как допущение с условием,
  при котором они будут заменены.

## 5. Полномочия и запреты

Разрешено: править только файлы в `practices/practice_01/`.

Запрещено:
- менять код в `app/` и сам `TRAINING_PR.diff`;
- approve или merge PR (SCOPE-1);
- ссылаться на внешний файл правил — правила берутся из раздела 2.4;
- придумывать новые ID правил;
- изменять раздел «P1-01 Findings» и строки P1-01 и P1-02 в `prompts.md`:
  это зафиксированные результаты прошлых запусков;
- вписывать оценку студента и результаты запусков, которых не было.

## 6. Рабочий процесс и остановка

1. Прочитать `TRAINING_PR.diff` целиком.
2. Заполнить `context.md` и `problem.md` — контекст и измеримые метрики.
3. Заполнить `analysis.md`, `product_management.md`,
   `project_management.md` — процесс, сценарии, план.
4. Заполнить `adr.md` — решение, альтернативы, схема.
5. Заполнить четыре файла тестов, разведя уровни ответственности.
6. Заполнить строку P1-03 в `prompts.md`.
7. Прогнать `make test` из корня репозитория.

Остановиться и спросить человека: при противоречии между источниками
и при необходимости требования, которого нет ни в диффе, ни в разделе 2.4.
Разрешать такое противоречие самостоятельно нельзя (SCOPE-1).

## 7. Проверки и подтверждения

- Каждый риск и каждое требование сопровождается evidence: цитатой из
  хунка или ID правила. Не подтверждённое — не включается (QA-1).
- Каждая проверка формулируется как конкретный вход и наблюдаемый
  критерий, а не как намерение («добавить тесты» — недопустимо).
- Уровни тестов разводятся по наблюдаемому критерию: unit — на
  перехваченном аргументе, integration — на стыке компонентов,
  load — время и доля отказов под потоком, e2e — код ответа клиенту.
- Метрики не содержат финансовых и опросных показателей: к учебному API
  они не привязаны ни одной строкой диффа.

## 8. Definition of Done

- Одиннадцать файлов заполнены без плейсхолдеров, `make test` проходит.
- У каждого утверждения есть evidence: хунк или ID правила.
- Ни одной ссылки на внешний файл правил; все правила названы по ID
  из раздела 2.4.
- Раздел «P1-01 Findings» и строки P1-01, P1-02 не изменены.
- Все одиннадцать файлов описывают один и тот же сценарий, а ссылки
  между ними указывают на существующие разделы.
