# Phase 0 — Research: UI заявки на бронирование

Неизвестных вида NEEDS CLARIFICATION в Technical Context не осталось: стек задан конституцией,
имена — контрактом, логика и API уже написаны командой 2. Исследование здесь — это решения по
местам, где контракт и спецификация оставляют UI свободу, и разбор чужого кода, который мы
импортируем.

---

## R-01. Как UI получает снимок расчёта

**Decision**: `src/main.js` хранит снимок в переменной модуля `estimate = { carId, days, extras, result }`.
Снимок заполняется в существующей функции `calculate()` **только после успешного** `calculateRental`
и обнуляется в существующей `clearResult()` (она уже вызывается на любой `input` в форме калькулятора
и при выборе машины из реестра). Состояние формы заявки — производное: `estimate === null` → «нет расчёта».

**Rationale**: `clearResult()` — уже существующая единственная точка сброса итога, в неё достаточно
добавить одну строку. Это автоматически даёт FR-015 («правка калькулятора возвращает форму в «нет
расчёта»») без второго источника правды.

**Alternatives considered**: читать снимок из DOM (`#calc-result`) — отклонено: парсить свою же
разметку обратно хрупко, а суммы там уже отформатированы строками. Хранить в `dataset` формы —
то же возражение, плюс состояние уехало бы в DOM, который перерисовывается.

## R-02. Машиночитаемые имена состояний

**Decision**: `BOOKING_STATES = { NO_ESTIMATE: 'no-estimate', EDITING: 'editing', SUBMITTING:
'submitting', SUCCESS: 'success', UNAVAILABLE: 'unavailable' }` в `src/booking-form.js`; значение
попадает в `data-state` на `<form>`. Русские подписи §7 живут отдельно в `BOOKING_TEXT.states` и
связаны со слагами 1:1.

**Rationale**: FR-020 требует машиночитаемый признак состояния, а контракт §7 даёт только русские
названия. Слаг — техническая запись того же состояния, объявленная в одном месте; новых состояний
не вводится.

**Alternatives considered**: писать в атрибут русские названия — отклонено: нестабильно для тестов
и селекторов. Завести свои названия состояний, отличные от §7 (например `idle`, `error`) — отклонено
прямо: это было бы второе имя в обход контракта (принцип V). Расхождение помечено в
`contracts/ui-modules.md` как предмет сверки с командой 2.

## R-03. Где граница между чистыми функциями и DOM

**Decision**: решения принимают чистые функции, DOM получает готовый результат.

- `src/booking-text.js` — все видимые строки и `errorView(code, field, context)`: по коду отдаёт
  `{ scope: 'field' | 'form', field, state, text }`.
- `src/booking-form.js` — `snapshotView`, `bookingPayload`, `checkDraft`, `responseView`,
  `confirmationView`: принимают данные, возвращают описание того, что показать.
- `src/main.js` — читает значения полей, зовёт функции, расставляет атрибуты и текст, делает `fetch`,
  считает таймаут. Ни одного `if` про коды ошибок, состояния или формулировки.

**Rationale**: принцип II — проверяемо только то, что не трогает DOM. Самое ценное для тестов
(«какой код → какое состояние и текст») уходит в `responseView`, которую можно прогнать на
литеральных объектах ответа без браузера и без сервера.

**Alternatives considered**: один модуль вместо двух — отклонено: тексты нужны и тестам разметки, и
логике состояний, а смешение «что написано» и «что показать» делает тесты текстов зависимыми от
автомата. Три модуля (отдельно сборка запроса) — лишнее дробление на таком объёме.

## R-04. Как UI различает три исхода отказа

**Decision**: `responseView(outcome)` принимает уже нормализованный `src/main.js` результат:
`{ kind: 'json', status, body }` либо `{ kind: 'timeout' | 'network' | 'unparsable' }`, и решает по
таблице §7:

1. `status` 201 или 200 → `success`, через `confirmationView`.
2. `status` 409 → `editing` + ошибка у `startDate` текстом из `conflictText(body.error.conflict)`.
3. `status` 400 с `error.code === 'validation_failed'` → разбор `error.fields`: коды полей
   `name`/`phone`/`startDate` дают ошибки у полей (состояние `editing`), а любой код полей
   `carId`/`days`/`extras` переводит в `no-estimate` с формой-сообщением «Расчёт устарел…» (FR-043).
   Если в ответе есть и то и другое — побеждает `no-estimate`: пересчёт всё равно обязателен.
4. `status` 5xx либо `kind !== 'json'` → `unavailable`.
5. всё прочее (`invalid_json`, `415`, `413`, `405`, `404`, нераспознанный код или имя поля) →
   `editing` + общее сообщение «Заявка не принята…».

**Rationale**: ровно порядок строк каталога §7, с одним добавленным правилом приоритета (пункт 3),
которого в каталоге нет, потому что там строки независимы.

**Alternatives considered**: показывать ошибки полей и «расчёт устарел» одновременно — отклонено:
в состоянии «нет расчёта» поля недоступны, ошибки рядом с ними посетитель всё равно исправить не
сможет.

## R-05. Таймаут и отмена запроса

**Decision**: `AbortController` + `setTimeout(() => controller.abort(), 10_000)` в `src/main.js`;
таймер снимается в `finally`. `AbortError` нормализуется в `{ kind: 'timeout' }`, сетевая ошибка
`fetch` — в `{ kind: 'network' }`, непрочитанный JSON — в `{ kind: 'unparsable' }`. Все три по §7
дают одно состояние «сервер недоступен».

**Rationale**: контракт §10 задаёт 10 с на стороне UI. `AbortController` — штатный браузерный API,
зависимостей не требует. Повторная отправка после таймаута безопасна благодаря §9: идентичная
заявка вернёт `200` с уже созданной бронью, а не `409`.

**Alternatives considered**: `Promise.race` без отмены — отклонено: запрос продолжал бы жить и мог
создать бронь уже после того, как UI сказал «не отправлено». С отменой возможна та же гонка, но §9
делает её безопасной для посетителя.

## R-06. Поле даты: тип и границы

**Decision**: `<input type="date">`. Его `value` — уже `YYYY-MM-DD`, ровно формат контракта §4, без
собственного разбора строк. Атрибуты `min` и `max` ставятся в `src/main.js` из `todayUtc()` и
`addDays(todayUtc(), BOOKING_HORIZON_DAYS)` — в разметку числа не прошиваются (FR-024).

**Rationale**: нативное поле даёт календарь, локализованный показ и ISO-значение одновременно;
`min`/`max` отсекают часть ошибок до отправки, но не заменяют проверку — значение можно ввести
руками, поэтому `validateBooking` всё равно вызывается.

**Alternatives considered**: текстовое поле с маской — отклонено: своя маска, свой разбор, свои
тексты про формат, и всё это уже умеет браузер. Три отдельных селекта день/месяц/год — больше кода
и хуже с клавиатуры.

## R-07. «Сегодня» в UTC против местного дня посетителя

**Decision**: UI берёт `todayUtc()` из `src/booking.js` (контракт §2) и для `min` поля, и для
проверки. Расхождение с местной датой посетителя принимается как есть.

**Rationale**: один календарь на обеих сторонах — иначе UI и сервер разошлись бы в оценке «дата в
прошлом». Контракт §2 прямо фиксирует UTC.

**Последствие, которое надо помнить**: посетитель восточнее UTC в первые часы своих суток увидит
«сегодня» на день раньше своего; посетитель западнее может получить `date_past` от сервера на дату,
которую UI считал валидной, если сутки UTC сменились между открытием страницы и отправкой. Второй
случай уже описан в спецификации как граничный (US2 №11) и обрабатывается как обычная ошибка поля.

**Alternatives considered**: местная дата в `min` — отклонено: дало бы поле, где выбранная дата
проходит в UI и падает на сервере.

## R-08. Ветка текста `name_length`

**Decision**: `errorView('name_length', 'name', { length })` выбирает формулировку по переданной
длине: `length < NAME_MIN_LENGTH` → «слишком короткое», иначе «слишком длинное». Константы берутся
из `src/booking.js` (`NAME_MIN_LENGTH`, `NAME_MAX_LENGTH`) и подставляются в текст.

**Rationale**: каталог §7 прямо говорит, что ветку выбирает UI «по собственному значению поля»:
сервер отдаёт один код `name_length` на оба случая. Длину считает вызывающий — так `errorView`
остаётся чистой и не дублирует правило подсчёта кодовых точек.

**Alternatives considered**: считать длину внутри `errorView` из `context.value` — рабочий вариант,
но тогда функция текстов начинает знать правило длины имени, которое уже реализовано в
`src/booking.js` (`codePointLength`). Передаём готовое число.

## R-09. Не сломают ли новые поля существующие тесты

**Decision**: секция `#booking` ставится **после** `</section>` калькулятора и до `#benefits`;
существующие тесты не правятся.

**Разбор по рискованным тестам `tests/index.test.js`**:

| Тест | Почему не ломается |
|---|---|
| «поле срока ограничено 1–30 сутками» — `html.match(/<input[\s\S]*?id="calc-days"[\s\S]*?\/>/)` ищет от **первого** `<input>` в документе | Поля заявки стоят ниже `#calc-days`, первый `<input>` в документе по-прежнему он. Комментарий в `index.html:75-76` предупреждает именно про `<input>` **выше** калькулятора |
| «поле срока связано с ошибкой через `aria-describedby`» — берёт первый `aria-describedby` в том же срезе | Срез кончается на `#calc-days`, наши атрибуты ниже |
| «сообщение об ошибке… до кнопки расчёта» — `html.indexOf('type="submit"')` | Первый `type="submit"` в документе — кнопка калькулятора (`index.html:143`), наша кнопка ниже |
| «у калькулятора есть выбор машины, срок и контейнер опций», «у каждого поля калькулятора есть label», «ошибка объявлена `role="alert"`» — срез `id="calculator"` … `id="benefits"`, в который попадёт и наша секция | Все проверки — на **наличие** (`assert.match`), добавление разметки их не нарушает |
| «автопарк строится скриптом», `!html.includes('data-car-id')` | В статической разметке заявки `data-car-id` не появляется: снимок расчёта рисуется скриптом и этого атрибута не использует |
| «все секции требований идут по порядку», «каждая внутренняя ссылка ведёт на существующий id» | `#booking` вставляется между `#calculator` и `#benefits`, порядок семи проверяемых секций сохраняется; ссылка в `<nav>` ведёт на существующий `id="booking"` |

**Rationale**: разместить форму внутри `#calculator` было бы ближе к букве «сразу после итога», но
FR-001 требует собственный `id` и ссылку в меню, а отдельная секция вдобавок не попадает в срезы
тестов калькулятора по своему `id`.

**Проверка**: `sh scripts/check.sh` после шага разметки — раньше, чем появятся стили и связка.

## R-10. Что делает «Оформить ещё одну заявку»

**Decision**: действие очищает поля заявки **и** сбрасывает итог калькулятора (вызывает существующую
`clearResult()`), то есть возвращает страницу в состояние «нет расчёта», как требует FR-017.

**Rationale**: иначе состояние противоречило бы экрану — расшифровка расчёта висела бы на месте,
а форма объявляла бы «сначала рассчитайте аренду». Единственный источник состояния — наличие снимка
(R-01), и сбрасывать надо именно его.

**Alternatives considered**: вернуть форму в «заполнение» с тем же снимком и пустыми полями — удобнее
для второй брони той же машины на другие даты, но расходится с FR-017. Если на приёмке это сочтут
неудобным, меняется FR-017 в спецификации, а не поведение в обход неё.

## Чужой код: что подтвердилось при чтении

- `src/booking.js` импортирует только `./cars.js`, `./calc.js`, `./format.js` — ни одного
  `node:`-импорта, поэтому модуль грузится браузером напрямую. Это заявлено в его шапке и проверено.
- `validateBooking(payload, today)` возвращает `{ ok, errors, value }`, где `errors` —
  `[{ field, code, message }]` в стабильном порядке `carId, days, extras, name, phone, startDate`.
  UI берёт `field` и `code`, а `message` игнорирует (контракт §5).
- `ERROR_CODES` экспортирован и заморожен — коды берутся оттуда, а не строковыми литералами.
- `NAME_MIN_LENGTH`, `NAME_MAX_LENGTH`, `BOOKING_HORIZON_DAYS` экспортированы — числа в текстах
  подставляются из них (R-08, R-06).
- `addDays` бросает `RangeError` на нечисловой сдвиг и на неверную дату — значит
  `conflictText` обязан проверять наличие и формат `conflict.endDate` **до** вызова, иначе исключение
  вместо текста. Отсюда ветка «при отсутствующем или непрочитанном `conflict`» (FR-025) реализуется
  через `try`/проверку, а не только через `conflict == null`.
- `formatDate` тоже бросает `RangeError` на неверном входе — та же осторожность в
  `confirmationView` для `booking.startDate`.
- `server.js` отдаёт статикой только `index.html`, `styles.css` и `src/**`, поэтому новые модули
  `src/booking-text.js` и `src/booking-form.js` доступны браузеру без правок сервера.
- `server.js` принимает `Content-Type` с параметрами (`application/json; charset=utf-8` пройдёт),
  так что заголовок можно ставить в привычном виде.
