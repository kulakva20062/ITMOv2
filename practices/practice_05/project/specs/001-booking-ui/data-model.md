# Phase 1 — Data Model: UI заявки на бронирование

Сущности здесь — это данные **в памяти страницы**. Персистентности на стороне UI нет: ни
`localStorage`, ни URL-состояния. Имена полей обмена берутся из контракта §4 и §5 и не
переопределяются.

---

## 1. Estimate — снимок расчёта

Основание заявки. Живёт в `src/main.js`, заполняется после успешного `calculateRental`.

| Поле | Тип | Источник | Примечание |
|---|---|---|---|
| `carId` | строка | значение `#calc-car` | `id` из `src/cars.js` |
| `days` | целое число | `#calc-days` через `Number()` | 1…30, уже прошло `calculateRental` |
| `extras` | массив строк | отмеченные `input[name="extras"]` | значения из `EXTRA_OPTIONS` |
| `result` | объект | ответ `calculateRental` | `{ base, discount, extrasTotal, insurance, total, deposit }` |

**Жизненный цикл**: `null` при загрузке → объект после успешного расчёта → снова `null` при любом
`input` в форме калькулятора, при выборе машины кнопкой «Рассчитать» в реестре и после «Оформить
ещё одну заявку».

**Инвариант**: `estimate === null` ⟺ состояние формы `no-estimate`. Второго источника правды нет.

---

## 2. Draft — черновик заявки

Три значения, которые вводит посетитель. Хранятся в самих полях DOM (единственное место, где
состояние законно живёт в разметке: это и есть ввод).

| Поле | Элемент | Тип значения | Правило |
|---|---|---|---|
| `name` | `#booking-name` | строка | §4: 2–60 символов после `trim`, буквы/пробел/дефис/апостроф, хотя бы одна буква |
| `phone` | `#booking-phone` | строка как введена | §6: после нормализации 11 цифр с `7` в начале |
| `startDate` | `#booking-date` | строка `YYYY-MM-DD` | §4: от «сегодня» UTC до +365 суток включительно |

**Инвариант**: черновик **не стирается** при ошибке, при «сервер недоступен» и при сбросе снимка
(FR-015, FR-019, FR-043). Очищается только после успеха действием «Оформить ещё одну заявку».

---

## 3. Payload — тело запроса

Собирается чистой функцией `bookingPayload(estimate, draft)`. Состав строго по контракту §4.

```text
{ carId, days, extras, name, phone, startDate }
```

Правила сборки:

- `carId`, `days`, `extras` — из `Estimate` на момент нажатия кнопки, не на момент открытия формы.
- `days` — число JSON, не строка.
- `extras` — массив; пустой выбор даёт `[]`, а не отсутствие поля.
- `phone` — как ввёл посетитель; нормализацию делает сервер.
- Суммы, `endDate`, `id`, `status`, `createdAt` **не отправляются**.

## 4. FormState — состояние формы

Ровно пять состояний контракта §7. Машиночитаемые слаги — `BOOKING_STATES` (решение R-02).

| Слаг | Подпись §7 | Поля | Кнопка | Что показано |
|---|---|---|---|---|
| `no-estimate` | нет расчёта | недоступны | недоступна | объяснение + ссылка на `#calculator`; либо «Расчёт устарел…» |
| `editing` | заполнение | доступны | доступна | снимок + поля; возможны ошибки полей и общее сообщение |
| `submitting` | отправка | недоступны | недоступна, подпись «Отправляем заявку…» | область состояния сообщает об отправке |
| `success` | успех | скрыты | скрыта | подтверждение + «Оформить ещё одну заявку» |
| `unavailable` | сервер недоступен | доступны | доступна | «Заявка не отправлена — сервер не ответил…», всё введённое на месте |

### Переходы

```text
                 появился итог расчёта
   no-estimate ──────────────────────────▶ editing
        ▲                                   │
        │ сброс итога / «ещё одну заявку»    │ отправка формы
        │ / отказ по carId|days|extras       ▼
        │                               submitting
        │                                   │
        │           ┌───────────────────────┼───────────────────────┐
        │           │ 201 / 200             │ 400 поля, 409,        │ 5xx, таймаут,
        │           ▼                       ▼ прочие 4xx            ▼ разрыв, неразбор
        │        success                 editing               unavailable
        │                                   │                       │
        └───────────────────────────────────┘                       │
                     отказ по снимку                                │
                                                                    │
                     editing ◀──────────────────────────────────────┘
                              повторная отправка
```

**Инварианты автомата**:

- Из `submitting` выход всегда есть: любой исход `fetch` отображён в §7, таймаут 10 с гарантирует
  выход даже при молчании сервера (R-05).
- `submitting` — единственное состояние, из которого нельзя отправить ещё раз (FR-016).
- Ошибки полей и занятые даты — признаки `editing`, а не отдельные состояния (FR-013).
- `success` покидается только действием «Оформить ещё одну заявку» → `no-estimate` (R-10).

## 5. FieldError — ошибка поля

Результат `errorView(code, field, context)`.

| Поле | Тип | Назначение |
|---|---|---|
| `scope` | `'field'` \| `'form'` | куда показывать: рядом с полем или в общем сообщении |
| `field` | `'name'` \| `'phone'` \| `'startDate'` \| `null` | у какого поля; `null` для общих |
| `state` | слаг из `BOOKING_STATES` | в какое состояние уводит эта строка §7 |
| `text` | строка | видимая формулировка из `BOOKING_TEXT` |

Соответствие «код → поле → состояние → текст» задано каталогом §7 и не дублируется здесь.
Контекст, который нужен тексту: `{ length }` для `name_length` (R-08), `{ horizon }` для
`date_too_far`, `{ from, to }` для `date_conflict`.

**Правило снятия**: ошибка поля снимается при событии `input` на **этом** поле; ошибки остальных
полей и общее сообщение не трогаются (FR-022).

## 6. Confirmation — подтверждение

Результат `confirmationView(booking, snapshotTotal)` из тела ответа `201`/`200`.

| Поле | Источник | Формат |
|---|---|---|
| `id` | `booking.id` | как есть, например `AD-0001` |
| `carModel` | `cars` по `booking.carId` | модель из `src/cars.js`, не из ответа |
| `startDate` | `booking.startDate` | `formatDate` → `ДД.ММ.ГГГГ` |
| `days` | `booking.days` | число + подпись суток |
| `total` | `booking.price.total` | `formatPrice` |
| `correction` | сравнение с `snapshotTotal` | строка об уточнении итога либо `null` (FR-018) |

**Чего здесь нет**: телефона посетителя (контракт §5 и §12 — показ телефона вне объёма),
`error.message`, `endDate` в ISO-виде, депозита из ответа (депозит посетитель видел в расчёте).

---

## 7. Чего в модели нет намеренно

- Занятых интервалов машины: `GET /api/cars/{carId}/busy` убран из v1 (§12), UI узнаёт о конфликте
  только из ответа `409`.
- Истории заявок и повторного поиска по номеру: `GET /api/bookings/{id}` в интерфейсе не
  используется (§12, FR вне объёма).
- Ключа идемпотентности: действует идемпотентность по содержимому (§9), своего ключа UI не хранит.
- Копии правил проверки: правила живут в `validateBooking` команды 2, UI их не повторяет.
