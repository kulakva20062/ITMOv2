# Контракт заявки на бронирование (booking) — команды UI и логики

**Статус**: согласован владельцем проекта 2026-10-23 по итогам сверки `specs/001-booking-ui/spec.md`
и `specs/002-booking-api/spec.md`.

**Версия**: 1.0.0

Этот документ — **единственный источник имён** полей, кодов ошибок, состояний UI и текстов
(принцип V конституции). Ни UI, ни логика не вводят своё имя поля, свой код или своё состояние
в обход контракта и не выводят их заново из кода другой стороны. Код, разошедшийся с контрактом,
правится по контракту. Изменение контракта — отдельный согласованный шаг обеих команд **до** правки кода.

Там, где спецификации команд расходятся с этим документом, действует этот документ.

---

## 1. Запуск: один origin

- Страницу и API отдаёт **один процесс Node 24** на встроенных модулях (`node:http`, `node:fs`),
  порт **8000**. Внешние пакеты не подключаются (принцип I).
- `GET /` и статические файлы (`index.html`, `styles.css`, `src/**`) — от того же сервера,
  что и `/api/**`. UI и API находятся на одном источнике, **CORS-заголовки не нужны**,
  обработка `OPTIONS` в v1 не требуется.
- На этапе реализации правятся (разрешено владельцем):
  - `package.json` → `scripts.start` запускает сервер Node вместо `python3 -m http.server 8000`;
  - `docs/requirements.md` → добавляется секция «Фича D: заявка на бронирование» с этим контрактом.
- HTTP-слой живёт отдельно от логики: чистые функции — в `src/`, сервер — в `server.js` в корне
  (принцип II, FR-036 спецификации логики).

## 2. «Сегодня», часовой пояс, горизонт

- Календарная арифметика и «сегодня» — **UTC** с обеих сторон.
- Канонический способ получить сегодняшнюю дату на обеих сторонах:
  `new Date().toISOString().slice(0, 10)` → `"YYYY-MM-DD"`.
- Текущая дата **передаётся параметром** в чистые функции проверки; функции к часам не обращаются
  (принцип II). К часам обращается только вызывающий слой: обработчик HTTP-запроса на сервере
  и обработчик отправки формы в UI.
- Сутки — календарные сутки UTC, без учёта переходов на летнее время.
- **Горизонт бронирования — `BOOKING_HORIZON_DAYS = 365`** суток вперёд от «сегодня» включительно.
  Число хранится в одном месте (`src/booking.js`) и подставляется в текст ошибки UI, а не прошивается строкой.

## 3. Общие модули `src/`, которые используют обе стороны

| Модуль | Экспорт | Кто использует | Примечание |
|---|---|---|---|
| `src/cars.js` | `cars` | UI, API | существующий, не меняется |
| `src/calc.js` | `calculateRental`, `MIN_DAYS` (1), `MAX_DAYS` (30), `EXTRA_OPTIONS`, `EXTRA_LABELS` | UI, API | существующий, **не меняется**; цена считается только им |
| `src/format.js` | `formatPrice`, `formatDate` | UI, API | `formatDate(iso)` → `ДД.ММ.ГГГГ`; суммы выводятся только через `formatPrice` |
| `src/booking.js` | `BOOKING_HORIZON_DAYS` (365), `todayUtc()`, `addDays(iso, n)`, `isValidName(value)`, `normalizePhone(value)`, `validateBooking(payload, today)`, `overlaps(a, b)`, `ERROR_CODES` | UI, API | новый; проверка полей — одна и та же на обеих сторонах |
| `src/booking-text.js` | `BOOKING_TEXT`, `errorView(code, field, context)` | UI | новый; все видимые строки формы, включая тексты из §7 |
| `src/booking-store.js` | хранилище в памяти: `add`, `findById`, `findSame`, `intervalsFor`, `clear` | API | новый; только сервер |

Проверка полей — **один предикат на обе стороны**: UI проверяет форму тем же `validateBooking`,
которым сервер проверяет запрос. Расхождение «UI считает валидным, сервер — нет» этим исключается
для всех полей, кроме тех, что зависят от состояния сервера (`date_conflict`).

## 4. Запрос

```http
POST /api/bookings HTTP/1.1
Content-Type: application/json
```

`Content-Type: application/json` **обязателен**; его отсутствие или другое значение → `415`.

```json
{
  "carId": "larus-16",
  "days": 3,
  "extras": ["child-seat", "full-insurance"],
  "name": "Иван Петров",
  "phone": "+7 000 000-00-00",
  "startDate": "2026-11-10"
}
```

| Поле | Тип JSON | Откуда у UI | Обязательно | Правило |
|---|---|---|---|---|
| `carId` | строка | выбранная машина калькулятора | да | равно `id` одной из `cars` |
| `days` | **целое число** (не строка) | поле «срок» калькулятора | да | `MIN_DAYS`…`MAX_DAYS` (1…30) |
| `extras` | массив строк | чекбоксы опций калькулятора | нет, по умолчанию `[]` | значения из `EXTRA_OPTIONS`, без повторов |
| `name` | строка | поле формы | да | 2–60 символов после `trim`; буквы (кириллица/латиница), пробел, дефис, апостроф; хотя бы одна буква |
| `phone` | строка, как ввёл посетитель | поле формы | да | см. §6 |
| `startDate` | строка `YYYY-MM-DD` | поле формы | да | существующая дата, от «сегодня» (UTC) до +`BOOKING_HORIZON_DAYS` включительно |

- `days` и `extras` берутся из снимка расчёта **на момент нажатия кнопки**, а не на момент открытия формы.
- UI **не отправляет** суммы, `endDate`, номер заявки, статус и дату создания. Присланные одноимённые
  поля сервер игнорирует (не ошибка).
- Неизвестные поля верхнего уровня игнорируются и в ответе не возвращаются.
- Телефон передаётся как введён; нормализацию делает сервер.
- Тело больше **8 КБ** не разбирается → `413`.
- Один отправленный запрос — один ответ. Защита от дубля на стороне UI — блокировка кнопки
  на время отправки; на стороне сервера — правило §9.

## 5. Ответы

### 201 Created — заявка принята

```http
201 Created
Location: /api/bookings/AD-0001
Content-Type: application/json; charset=utf-8
```

```json
{
  "id": "AD-0001",
  "status": "confirmed",
  "carId": "larus-16",
  "startDate": "2026-11-10",
  "endDate": "2026-11-13",
  "days": 3,
  "extras": ["child-seat", "full-insurance"],
  "customer": { "name": "Иван Петров", "phone": "+70000000000" },
  "price": {
    "base": 7200, "discount": 0, "extrasTotal": 900,
    "insurance": 1080, "total": 9180, "deposit": 10000
  },
  "createdAt": "2026-10-23T12:00:00.000Z"
}
```

- Номер: `AD-` + порядковый номер не менее 4 цифр с ведущими нулями (`AD-0001` … `AD-9999`, `AD-10000`).
  Выдаётся последовательно, не переиспользуется в пределах жизни процесса; отклонённая заявка номер не расходует.
- `endDate` = `startDate` + `days` суток (день возврата, см. §8).
- `extras` возвращаются в порядке `EXTRA_OPTIONS`, независимо от порядка в запросе.
- `price` — ровно шесть сумм из `calculateRental({ carId, days, extras })`, целые рубли. Залог в `total` не входит.
  Цена фиксируется в момент приёма: позднее изменение прайса в `src/cars.js` её не меняет.
- `customer.name` — как ввёл посетитель, обрезанный по краям; `customer.phone` — нормализованный.
- UI показывает в подтверждении: номер, машину (по `carId` из `src/cars.js`), дату начала, срок и
  `price.total` через `formatPrice`. **Телефон в подтверждении не показывается.**
- Если `price.total` отличается от итога в снимке расчёта, UI дополнительно показывает строку об
  уточнении итога с обеими суммами (в норме суммы совпадают — обе стороны считают одним `calculateRental`).

### 200 OK — повторная идентичная заявка (§9) и `GET /api/bookings/{id}`

Тело — то же, что у `201`. Заголовок `Location` не отправляется.

### 400 / 409 / прочие — ошибка

Единая форма тела для **всех** ошибок:

```json
{ "error": { "code": "...", "message": "...", "fields": [ ... ] } }
```

- `fields` — массив всегда; пустой, если ошибка не про поля.
- Каждая запись: `{ "field": "...", "code": "...", "message": "..." }`.
- Порядок записей стабилен: `carId`, `days`, `extras`, `name`, `phone`, `startDate`.
- Проверка собирает ошибки по всем полям за один проход и не останавливается на первой.
- Проверка полей выполняется **до** проверки занятости; при непройденной проверке занятость не
  проверяется и хранилище не меняется.
- `message` — человеческая формулировка на русском из `src/`. **UI её не показывает** (§7);
  она существует для `curl`, логов и тестов API.
- Любой ответ с телом имеет `Content-Type: application/json; charset=utf-8`. HTML и стектрейсы не отдаются.

400 `validation_failed`:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте поля заявки: 3 поля заполнены неверно.",
    "fields": [
      { "field": "days", "code": "days_out_of_range", "message": "Срок аренды — целое число суток от 1 до 30. Получено: 0." },
      { "field": "name", "code": "name_length", "message": "Имя — от 2 до 60 символов." },
      { "field": "phone", "code": "phone_invalid", "message": "Телефон — 11 цифр, например +7 000 000-00-00. Получено цифр: 3." }
    ]
  }
}
```

409 `date_conflict` — поле `conflict` **обязательно**:

```json
{
  "error": {
    "code": "date_conflict",
    "message": "Эта машина занята с 10.11.2026 по 12.11.2026. Выберите другие даты или другую машину.",
    "fields": [{ "field": "startDate", "code": "date_conflict", "message": "Занято с 10.11.2026 по 12.11.2026." }],
    "conflict": { "carId": "larus-16", "startDate": "2026-11-10", "endDate": "2026-11-13" }
  }
}
```

`conflict.startDate` и `conflict.endDate` — **ISO-даты полуоткрытого интервала** (§8). Если пересечений
несколько, называется первый по `startDate`. Имя и телефон из чужой заявки не раскрываются.
UI форматирует даты сам через `formatDate` из `src/format.js`.

### Коды ответов

| Код | Когда | `error.code` |
|---|---|---|
| `201` | заявка принята | — |
| `200` | повторная идентичная заявка (§9); `GET /api/bookings/{id}` | — |
| `400` | не прошла проверка полей | `validation_failed` |
| `400` | тело не разбирается как JSON (включая пустое) | `invalid_json` |
| `404` | нет такой заявки | `booking_not_found` |
| `404` | неизвестный путь | `not_found` |
| `405` | известный путь, неподдерживаемый метод (+ заголовок `Allow`) | `method_not_allowed` |
| `409` | пересечение дат на этой машине | `date_conflict` |
| `413` | тело больше 8 КБ | `payload_too_large` |
| `415` | нет или не тот `Content-Type` | `unsupported_media_type` |
| `500` | непредвиденный сбой (без внутренних подробностей) | `internal_error` |

После `500` процесс продолжает обслуживать запросы.

### Ручки v1

```http
POST /api/bookings        → 201 | 200 (§9) | 400 | 409 | 413 | 415 | 500
GET  /api/bookings/{id}   → 200 (тело заявки) | 404 booking_not_found
```

`GET /api/bookings/{id}` не требует авторизации и возвращает имя и телефон — допустимо только потому,
что данные вымышленные, а хранилище живёт в памяти демо-процесса.

## 6. Правило телефона

Принимаются цифры, пробелы, дефисы, круглые скобки и необязательный ведущий `+`. После удаления
нецифровых символов и замены ведущей `8` на `7` должно получиться ровно **11 цифр, начинающихся с `7`**.
Нормализованный вид: `+7XXXXXXXXXX`. Заглушка `+7 000 000-00-00` проходит проверку.

| Значение | Вердикт |
|---|---|
| `"+7 000 000-00-00"`, `"80000000000"`, `"+7 (000) 000-00-00"` | принято → `+70000000000` |
| `"0000000000"` (10 цифр), `"700000000000"` (12 цифр), `"+10000000000"` | `phone_invalid` |
| `"телефон"`, `"+7-000-000-00-0a"` | `phone_charset` |
| `""`, `"   "`, отсутствует, `null` | `required` |

## 7. Каталог: код → поле → состояние UI → текст UI

UI рендерит **по `code`**, а не по `message`. Все видимые строки — из `src/booking-text.js`.
Состояния формы: «нет расчёта», «заполнение», «отправка», «успех», «сервер недоступен».
Машиночитаемые имена (`data-state`, `BOOKING_STATES`): `no-estimate`, `editing`, `submitting`,
`success`, `unavailable` — в том же порядке. Используются только UI; API их не знает.
Ошибки полей — видимые признаки состояния «заполнение», а не отдельные состояния.

| `error.code` / `fields[].code` | Поле | HTTP | Состояние UI | Текст UI |
|---|---|---|---|---|
| `required` | `name` | 400 | заполнение, ошибка у поля | Укажите имя — так мы обратимся к вам при подтверждении. |
| `name_length` | `name` | 400 | заполнение, ошибка у поля | длина < 2: «Имя слишком короткое — не меньше 2 символов.»; длина > 60: «Имя слишком длинное — не больше 60 символов.» (ветку выбирает UI по собственному значению поля) |
| `name_charset` | `name` | 400 | заполнение, ошибка у поля | Имя — только буквы, пробел, дефис и апостроф. |
| `required` | `phone` | 400 | заполнение, ошибка у поля | Укажите телефон — на него мы позвоним для подтверждения. |
| `phone_charset` | `phone` | 400 | заполнение, ошибка у поля | Телефон должен содержать 11 цифр, например +7 000 000-00-00. |
| `phone_invalid` | `phone` | 400 | заполнение, ошибка у поля | Телефон должен содержать 11 цифр, например +7 000 000-00-00. |
| `required` | `startDate` | 400 | заполнение, ошибка у поля | Выберите дату начала аренды. |
| `date_format` | `startDate` | 400 | заполнение, ошибка у поля | Выберите дату начала аренды. |
| `date_invalid` | `startDate` | 400 | заполнение, ошибка у поля | Выберите дату начала аренды. |
| `date_past` | `startDate` | 400 | заполнение, ошибка у поля | Дата начала не может быть в прошлом — выберите сегодня или позже. |
| `date_too_far` | `startDate` | 400 | заполнение, ошибка у поля | Дата начала не дальше {`BOOKING_HORIZON_DAYS`} дней от сегодня. |
| `date_conflict` | `startDate` | 409 | заполнение, ошибка у поля даты | Эта машина занята с {`formatDate(conflict.startDate)`} по {`formatDate(addDays(conflict.endDate, -1))`}. Выберите другую дату начала или другую машину. При отсутствии или непрочитанном `conflict`: «Эта машина уже занята на выбранные даты. Выберите другую дату начала или другую машину.» |
| `required`, `car_unknown` | `carId` | 400 | **нет расчёта**, общее сообщение | Расчёт устарел — пересчитайте стоимость в калькуляторе. |
| `days_not_integer`, `days_out_of_range`, `required` | `days` | 400 | **нет расчёта**, общее сообщение | Расчёт устарел — пересчитайте стоимость в калькуляторе. |
| `extras_not_array`, `extra_unknown`, `extras_duplicate` | `extras` | 400 | **нет расчёта**, общее сообщение | Расчёт устарел — пересчитайте стоимость в калькуляторе. |
| `invalid_json`, `unsupported_media_type`, `payload_too_large`, `method_not_allowed`, `not_found`, `booking_not_found` | — | 400/415/413/405/404 | заполнение, общее сообщение над кнопкой | Заявка не принята. Проверьте поля и отправьте ещё раз. |
| нераспознанный код или нераспознанное имя поля | — | любой 4xx | заполнение, общее сообщение над кнопкой | Заявка не принята. Проверьте поля и отправьте ещё раз. |
| `internal_error`, любой 5xx, таймаут, разрыв связи, неразобранный ответ | — | 5xx / нет ответа | **сервер недоступен** | Заявка не отправлена — сервер не ответил. Проверьте связь и нажмите «Отправить заявку» ещё раз. |

Правила показа:

- Ошибка поля показывается рядом с этим полем, снимается при изменении значения **этого** поля и не
  влияет на ошибки других полей. Поле с ошибкой: `aria-invalid="true"` и программная связь с текстом
  ошибки; текст ошибки — `role="alert"`, цвет `--stamp`.
- При отправке с ошибками фокус переходит на первое поле с ошибкой в визуальном порядке.
- Область состояния — `role="status"`, фокус не перехватывает; области состояния и ошибок присутствуют
  в разметке постоянно и пустуют, когда сообщать нечего.
- В состояниях «заполнение» (с любыми ошибками) и «сервер недоступен» введённые значения сохраняются.
- При переходе в «нет расчёта» (строки `carId` / `days` / `extras`) имя, телефон и дата **сохраняются**;
  показывается ссылка на калькулятор.
- Из ответа сервера UI берёт только: номер заявки, суммы, `carId`, даты, срок и границы `conflict`.
  Формулировки для показа из ответа не берутся никогда.

## 8. Правило интервала и пересечения

- Занятый машиной период — **полуоткрытый интервал** календарных суток UTC `[startDate, endDate)`,
  где `endDate` = `startDate` + `days` суток. День `endDate` — день возврата, он **свободен** для новой аренды.
- Две заявки на одну машину пересекаются тогда и только тогда, когда `aStart < bEnd && bStart < aEnd`.
  Касание встык (`aEnd == bStart`) пересечением не является.
- Правило действует только в пределах одного `carId`.
- В API интервалы всегда полуоткрытые. **В тексте UI показывается последний занятый день**
  = `addDays(conflict.endDate, -1)`. Пример: занято `[2026-11-10, 2026-11-13)` → UI пишет
  «занята с 10.11.2026 по 12.11.2026», и заявка на 13.11.2026 проходит.

Проверка занятости и запись заявки — один неделимый шаг обработки запроса, без `await` между ними.

## 9. Повторная отправка (идемпотентность по содержимому)

Если прошедшая проверку заявка **полностью совпадает** с уже принятой, сервер возвращает `200` с телом
существующей заявки и **не создаёт** новую бронь и новый номер. Это правило проверяется **до** правила
пересечения дат.

Ключ совпадения — набор: `carId`, `startDate`, `days`, `extras` (сравниваются как множества, порядок
не важен), `name` после `trim`, `phone` после нормализации. Несовпадение хотя бы в одном поле —
обычная новая заявка, и при пересечении дат она получает `409`.

Обоснование: ответ может потеряться по сети, UI покажет «сервер недоступен» и предложит нажать кнопку
ещё раз. Без этого правила посетитель получил бы `409` «машина занята» от собственной брони.
Заголовок-ключ идемпотентности в v1 не вводится.

## 10. Бюджет времени

- Сервер отвечает за **≤ 2 с** на любой запрос (хранилище в памяти).
- UI ждёт ответ **10 с**; по истечении — состояние «сервер недоступен». Заявка при этом считается
  неотправленной с точки зрения UI; повторное нажатие безопасно благодаря §9.
- Во время отправки кнопка и поля недоступны, второй запрос не уходит.

## 11. Хранение

- Заявки живут в памяти процесса. База данных, файлы и внешние сервисы не используются.
- Перезапуск процесса: хранилище пусто, нумерация с `AD-0001`, `GET` прежнего номера → `404`.
  Это принятое ограничение, а не дефект; UI не предлагает посетителю найти заявку позже.
- Операции хранилища: добавить, найти по номеру, найти идентичную (§9), перечислить интервалы машины,
  очистить всё (для тестов).

## 12. Вне объёма v1

- `GET /api/cars/{carId}/busy` и любая предзагрузка занятых дат в UI (убрано из v1).
- Заголовок-ключ идемпотентности (`Idempotency-Key`).
- CORS, `OPTIONS`, работа UI и API на разных портах.
- Авторизация, оплата, e-mail/SMS, отмена и изменение заявки, личный кабинет, админка.
- Статусы заявки, кроме `confirmed`.
- Международные телефоны.
- Показ телефона в подтверждении.
- Лимит числа заявок в хранилище и вытеснение.
- Правки `src/calc.js`: правила расчёта, границы `MIN_DAYS`/`MAX_DAYS` и набор `EXTRA_OPTIONS`
  переиспользуются без изменений.

- Тесты покрывают каждую строку каталога §7 и правила §8 и §9.
- Ранее принятые сценарии лендинга, калькулятора и фильтра автопарка остаются выполненными.
- Все данные вымышленные: `+7 000 000-00-00`, `hello@example.com`; внешних ресурсов нет (принцип IV).
