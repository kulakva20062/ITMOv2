# Tasks: Логика и API заявки на бронирование (booking-api)

**Input**: Design documents from `specs/002-booking-api/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/internal-modules.md](./contracts/internal-modules.md), [quickstart.md](./quickstart.md)

**Источник имён**: [`specs/contracts/booking-contract.md`](../contracts/booking-contract.md) v1.0.0 — ни одна задача не вводит имени поля, кода ошибки или видимого текста вне контракта.

**Tests**: обязательны. Спецификация требует их прямо (FR-037, SC-010), конституция — принципами II и III.

## Формат: `[ID] [P?] [Story] Описание`

- **[P]**: можно делать параллельно (разные файлы, нет зависимости от незавершённых задач)
- **[Story]**: к какой user story относится задача (US1…US4)
- В описании — точные пути файлов

## Два правила, отличающие этот список от шаблона

1. **Тесты и модуль — в одной задаче, а не «сначала красные тесты».** Конституция III требует
   зелёного `sh scripts/check.sh` **после каждой правки**, поэтому «оставить раннер красным
   до следующей задачи» запрещено. Внутри задачи порядок всё равно TDD: сначала тест из
   таблицы граничных значений, потом код до зелёного.
2. **`server.js` правится в нескольких фазах** (обработчик наращивается шагами R-03), поэтому
   задачи, трогающие его, никогда не помечены `[P]` друг относительно друга.

## Path Conventions

Плоская раскладка проекта: чистые функции — `src/`, тесты — `tests/`, сервер — `server.js` в
корне (см. plan.md → Structure Decision). Каталоги `models/`, `services/` не вводятся.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: без зависимостей, можно начинать сразу
- **Foundational (Phase 2)**: после Setup (T001 нужен для T019) — **блокирует все истории**
- **User Stories (Phase 3–6)**: после Phase 2; по приоритету P1 → P2 → P3 → P4
- **Polish (Phase 7)**: после всех желаемых историй

### User Story Dependencies

- **US1 (P1)**: только Phase 2. Независима — это MVP
- **US2 (P2)**: Phase 2 + T012 из US1 (шаг занятости встраивается в тот же обработчик). Проверяема отдельно
- **US3 (P3)**: Phase 2 + T012 из US1. Проверяема отдельно
- **US4 (P4)**: Phase 2 + T018 (US2) и T023 (US3) — правило §9 стоит в конвейере между их шагами. Проверяема отдельно

Истории не независимы по файлу `server.js`: обработчик один и наращивается шагами R-03.
По **поведению** каждая история проверяется отдельно, по **правкам** — последовательно.

### Within Each User Story

- Тест и код — в одной задаче (правило 2 выше); внутри задачи сначала тест
- Чистые функции `src/` → шаг обработчика в `server.js` → сквозные тесты
- История завершена и раннер зелёный до перехода к следующему приоритету

### Parallel Opportunities

- Phase 1: T001, T002, T003 — три разных файла, все `[P]`
- Phase 2: T005, T008, T009 параллельны друг другу (T005 и T008 — разные функции одного модуля, но независимые экспорты; T009 — отдельный файл). T004 → T006 → T007 строго последовательны. T010 параллелен T005–T009
- Phase 3: T012 → T013, затем T014–T017 все `[P]` (разные блоки тестов одного файла, независимые)
- Phase 4: T018 → T019, затем T020–T022 все `[P]`
- Phase 5: T023 и T024 последовательны по `server.js`, затем T025–T027 все `[P]`

## Implementation Strategy

### MVP First (только US1)

1. Phase 1: Setup (T001–T003)
2. Phase 2: Foundational (T004–T011) — блокирует всё
3. Phase 3: US1 (T012–T017)
4. **СТОП и ПРОВЕРКА**: сценарии 3.1 и 3.2 quickstart.md, `sh scripts/check.sh` зелёный
5. Показать: заявка принимается, номер выдаётся, цена совпадает с калькулятором

### Incremental Delivery

1. Setup + Foundational → сервер поднимается, статика отдаётся, чистые функции под тестами
2. + US1 → заявка принимается и читается по номеру (**MVP**)
3. + US2 → двойная бронь невозможна
4. + US3 → любой некорректный запрос получает разбор по полям
5. + US4 → повторное нажатие кнопки не создаёт вторую бронь
6. Phase 7 → сквозные аудиты и приёмка

Каждый шаг оставляет `sh scripts/check.sh` зелёным и не ломает предыдущие (принцип III).

### Parallel Team Strategy

Внутри команды 2 истории плохо делятся: все шаги живут в одном обработчике `server.js`.
Делится иначе — по слоям: один разработчик ведёт чистые функции `src/booking.js` и
`src/booking-store.js` с модульными тестами (T004–T009), второй — `server.js` и сквозные
тесты (T010 и далее). Точка стыковки — контракт `contracts/internal-modules.md`.

Параллельно с командой 1 работа идёт без конфликтов, кроме `src/format.js` — см. T035.
