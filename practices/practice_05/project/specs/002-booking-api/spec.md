## Обзор

Посетитель AutoDrive, посчитав стоимость в калькуляторе, отправляет заявку на бронирование
выбранной машины: имя, телефон, дата начала аренды. Срок и опции приходят из снимка расчёта.
Сервер проверяет заявку поле за полем тем же предикатом, которым проверяет форму UI, **сам**
пересчитывает цену по правилам `src/calc.js`, узнаёт повторную отправку по содержимому,
отказывает, если машина занята на пересекающиеся даты, и отвечает номером заявки. Заявки живут
в памяти процесса и исчезают при его перезапуске.

Страницу и API отдаёт один процесс Node 24 на порту 8000 (контракт §1), поэтому вопросов
кросс-доменного доступа у этой фичи нет.

Вне объёма — список контракта §12. Отдельно отмечу главное: вёрстка и поведение формы (объём
команды 1), `GET /api/cars/{carId}/busy` и предзагрузка занятых дат, CORS и `OPTIONS`, заголовок
`Idempotency-Key`, правки `src/calc.js`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Заявка уходит на сервер и получает номер (Priority: P1)

Посетитель выбрал машину, срок и опции в калькуляторе, ввёл имя, телефон и дату начала аренды
и отправил заявку. Сервер принимает её, считает цену сам и возвращает номер заявки вместе с
расшифровкой стоимости и датой окончания аренды. Посетитель видит номер и может назвать его
при звонке.

**Why this priority**: это и есть продукт — без принятой заявки с номером остальное не нужно.

**Independent Test**: отправить корректную заявку на свободную машину и проверить, что в ответе
есть номер заявки, срок, дата окончания и суммы, совпадающие с `calculateRental`.

**Acceptance Scenarios**:

1. **Given** пустое хранилище и корректная заявка (`carId: 'larus-16'`, `days: 3`, `extras: []`, имя, телефон, дата начала), **When** заявка отправлена, **Then** `201`, тело по форме контракта §5, номер `AD-0001`, статус `confirmed`, цена `base 7200, discount 0, extrasTotal 0, insurance 0, total 7200, deposit 10000`.
2. **Given** та же заявка, **When** она принята, **Then** в ответе `endDate` = дата начала + `days` суток (контракт §8), а `days` совпадает с отправленным.
3. **Given** принятая заявка `AD-0001`, **When** отправлена корректная заявка на другую машину, **Then** её номер — `AD-0002`; нумерация последовательна и не переиспользуется (контракт §5).
4. **Given** заявка с опциями `['child-seat', 'full-insurance']` и `days: 7`, **When** она принята, **Then** шесть сумм в `price` равны результату `calculateRental({ carId, days, extras })` — сервер не пересчитывает по своим правилам и не доверяет суммам из запроса.
5. **Given** в запросе дополнительно переданы `total`, `endDate`, `id`, `status`, `createdAt` и неизвестное поле `foo`, **When** заявка отправлена, **Then** все они игнорируются без ошибки; в ответе — серверные значения, поля `foo` в ответе нет (контракт §4).
6. **Given** заявка с `extras: ['full-insurance', 'child-seat']`, **When** она принята, **Then** в ответе `extras` перечислены в порядке `EXTRA_OPTIONS` из `src/calc.js` (контракт §5).
7. **Given** принятая заявка `AD-0001`, **When** выполнен `GET /api/bookings/AD-0001`, **Then** `200` с тем же телом и **без** заголовка `Location`; **When** выполнен `GET /api/bookings/AD-9999`, **Then** `404` `booking_not_found`.
8. **Given** запущенный процесс, **When** запрошен `GET /` и `GET /styles.css`, **Then** страница и статика отдаются тем же сервером, что и `/api/**` (контракт §1).

### User Story 2 - Машину нельзя забронировать дважды на пересекающиеся даты (Priority: P2)

Если на выбранную машину уже есть **другая** заявка, чьи даты пересекаются с новой, сервер
отказывает и называет занятый интервал, чтобы посетитель выбрал другие даты или другую машину.

**Why this priority**: без этого правила продукт обещает занятую машину — ошибка дороже, чем
отказ в приёме заявки.

**Independent Test**: принять заявку, затем отправить другую (отличающуюся хотя бы именем) на ту
же машину с пересечением — получить `409`; и с касанием встык — получить `201`.

**Acceptance Scenarios**:

1. **Given** принята заявка `larus-16` c `startDate 2026-11-10`, `days: 3` (занят интервал `[2026-11-10, 2026-11-13)`), **When** приходит заявка `larus-16` c `startDate 2026-11-12`, `days: 2` **от другого посетителя**, **Then** `409` `date_conflict`, в теле обязательное поле `conflict` = `{ carId: 'larus-16', startDate: '2026-11-10', endDate: '2026-11-13' }` (ISO-даты полуоткрытого интервала, контракт §5 и §8).
2. **Given** та же принятая заявка, **When** приходит заявка `larus-16` c `startDate 2026-11-13` (день возврата предыдущей), **Then** `201`: интервалы встык не пересекаются.
3. **Given** та же принятая заявка, **When** приходит заявка `larus-16` c `startDate 2026-11-07`, `days: 3`, **Then** `201` (встык слева).
4. **Given** та же принятая заявка, **When** приходит заявка на **другую** машину с теми же датами, **Then** `201`: правило действует в пределах одного `carId`.
5. **Given** та же принятая заявка, **When** приходит заявка `larus-16` c `startDate 2026-11-09`, `days: 10` (новый интервал полностью накрывает занятый), **Then** `409`.
6. **Given** на `larus-16` приняты две заявки с пересечением новой, **When** приходит новая заявка, **Then** в `conflict` назван первый по `startDate` интервал (контракт §5).
7. **Given** конфликт возник, **When** UI читает ответ, **Then** имя и телефон из чужой заявки в теле отсутствуют; последний занятый день UI выводит сам как `addDays(conflict.endDate, -1)` (контракт §8) — сервер готовых формулировок для показа не присылает.
8. **Given** две одновременные заявки на один и тот же свободный интервал, **When** они обработаны, **Then** принята ровно одна, вторая получает `409`: проверка занятости и запись — один неделимый шаг без `await` между ними (контракт §8).

### User Story 3 - Неверные данные отклоняются с разбором по полям (Priority: P3)

Посетитель ошибся в телефоне или выбрал прошедшую дату. Сервер не принимает заявку, не меняет
хранилище и возвращает список полей с кодом по каждому, чтобы UI подсветил именно эти поля.

**Why this priority**: правило нужно для надёжности, но демонстрируется только после того, как
успешный путь работает.

**Independent Test**: отправить заявку, где сломаны сразу три поля, и проверить, что в ответе
перечислены все три поля с кодами из контракта §7, а хранилище осталось пустым.

**Acceptance Scenarios**:

1. **Given** пустое хранилище, **When** приходит заявка с `name: 'A'`, `phone: '123'`, `days: 0`, **Then** `400` `validation_failed` и три записи в `fields` — `days`, `name`, `phone` именно в этом порядке (контракт §5); хранилище пусто.
2. **Given** заявка с неизвестным `carId`, **When** она отправлена, **Then** `400`, поле `carId`, код `car_unknown`.
3. **Given** заявка с `startDate` на день раньше текущей даты UTC, **When** она отправлена, **Then** `400`, поле `startDate`, код `date_past`.
4. **Given** тело запроса не разбирается как JSON (включая пустое тело), **When** оно отправлено, **Then** `400` `invalid_json` и `fields: []`.
5. **Given** корректная заявка, у которой проверка проходит, но машина занята, **When** она отправлена, **Then** возвращается `409`, а не `400`: проверка полей выполняется до проверки занятости (контракт §5).
6. **Given** отсутствующий или иной `Content-Type`, **When** отправлено тело, **Then** `415` `unsupported_media_type`; **Given** тело больше 8 КБ, **Then** `413` `payload_too_large` и тело не разбирается.
7. **Given** запрос `DELETE /api/bookings`, **When** он отправлен, **Then** `405` `method_not_allowed` с заголовком `Allow`; **Given** запрос `GET /api/unknown`, **Then** `404` `not_found`.
8. **Given** любой из этих отказов, **When** прочитано тело, **Then** оно имеет единую форму контракта §5 с массивом `fields` (пустым, если ошибка не про поля) и `Content-Type: application/json; charset=utf-8`; HTML и стектрейсы не отдаются.
9. **Given** обработчик сломался непредвиденно, **When** запрос завершён, **Then** `500` `internal_error` без внутренних подробностей, и следующий запрос обслуживается нормально.
10. **Given** поле `message` в теле ошибки, **When** UI обрабатывает ответ, **Then** UI рендерит по `code` и `message` не показывает (контракт §5 и §7): `message` существует для `curl`, логов и тестов API.

### User Story 4 - Повторная отправка не создаёт вторую бронь (Priority: P4)

Ответ сервера может потеряться по сети: UI покажет «сервер недоступен» и предложит нажать
кнопку ещё раз. Повторная **полностью идентичная** заявка возвращает ту же бронь с тем же
номером, а не отказ «машина занята».

**Why this priority**: сценарий редкий, но без него посетитель получает `409` от собственной
брони — отказ, который невозможно исправить.

**Independent Test**: отправить одну и ту же заявку дважды и проверить, что номер один и тот же,
а в хранилище одна запись.

**Acceptance Scenarios**:

1. **Given** принятая заявка `AD-0001`, **When** то же тело отправлено ещё раз, **Then** `200` с телом `AD-0001`, **без** заголовка `Location`; новая бронь и новый номер не создаются (контракт §9).
2. **Given** принятая заявка, **When** повтор отличается только порядком `extras`, пробелами по краям `name` или записью телефона, нормализующейся в то же значение, **Then** это считается той же заявкой: `200` с прежним номером (ключ совпадения — контракт §9).
3. **Given** принятая заявка, **When** повтор отличается именем, телефоном, сроком, датой, машиной или набором опций, **Then** это новая заявка: `201`, если даты свободны, и `409`, если пересекаются.
4. **Given** принятая заявка, **When** приходит её точный повтор, **Then** правило §9 применяется **до** правила пересечения: `409` в этом случае не возникает.
5. **Given** заявка не прошла проверку полей, **When** она отправлена дважды, **Then** оба раза `400`, номер не расходуется, хранилище пусто.

### Edge Cases

Граничные значения собраны в разделе «Граничные значения» — здесь только нетабличные случаи.

- **Срок пересекает конец месяца и года.** `startDate 2026-12-30`, `days: 3` → `endDate 2027-01-02`. Арифметика — календарные сутки UTC, без переходов на летнее время (контракт §2).
- **29 февраля.** `startDate 2028-02-28`, `days: 2` → `endDate 2028-03-01` (2028 — високосный).
- **«Сегодня» на границе суток.** Текущая дата — входной параметр проверки (`validateBooking(payload, today)`), а не обращение к часам внутри функции; сервер подставляет `todayUtc()` в момент запроса. Заявка в 23:59:59 UTC и заявка секундой позже могут получить разные вердикты по `date_past` — это ожидаемо.
- **Дубли опций.** `['child-seat', 'child-seat']` — `extras_duplicate`, а не молчаливое удвоение цены. При этом в ключе повторной отправки (§9) `extras` сравниваются как множества — проверка и сравнение решают разные задачи и не противоречат друг другу.
- **Порядок опций.** `['full-insurance', 'child-seat']` и `['child-seat', 'full-insurance']` дают одну цену; в ответе порядок — по `EXTRA_OPTIONS`.
- **Пробелы и регистр.** Имя и телефон обрезаются по краям до проверки; имя сохраняется как ввёл посетитель (регистр не меняется), телефон — нормализованным `+7XXXXXXXXXX`.
- **Телефон с `8` в начале.** `8 000 000-00-00` → `+70000000000`, принято (контракт §6).
- **Отсутствующее поле и `null`.** Трактуются одинаково: `required`.
- **`extras` отсутствует.** Трактуется как `[]` — это не ошибка (контракт §4).
- **Расчёт устарел.** Ошибки по `carId`, `days`, `extras` означают, что снимок расчёта разошёлся с правилами; сервер отдаёт обычный `400` с кодами по этим полям, а UI переходит в состояние «нет расчёта» (контракт §7). Сервер о состояниях UI ничего не знает и ничего для них не присылает.
- **`RangeError` из `calculateRental`.** В нормальной работе недостижим: расчёт вызывается только на данных, прошедших проверку. Если он всё же возник — это `500` `internal_error`, а не `400`.
- **Перезапуск процесса.** Все заявки теряются, нумерация начинается с `AD-0001`, ранее выданный номер → `404`. Принятое ограничение (контракт §11).
- **Запрос неизвестного пути или метода.** Отвечает `404` / `405` в единой форме JSON, а не падает и не отдаёт HTML.
- **Статика и API делят маршрутизацию.** Путь, начинающийся с `/api/`, никогда не отдаётся как файл; путь за пределами корня проекта не читается с диска.

## Requirements *(mandatory)*

Имена полей, типы, коды и тексты — по контракту. Требования ниже задают **поведение сервера**
и минимум покрытия тестами.

### Functional Requirements

#### Данные заявки

- **FR-001**: Заявка MUST состоять ровно из шести полей от UI, перечисленных в контракте §4: `carId`, `days`, `extras`, `name`, `phone`, `startDate`. `days` и `extras` берутся из снимка расчёта на момент нажатия кнопки.
- **FR-002**: Система MUST NOT принимать от клиента цену, номер, статус, дату окончания и дату создания: эти значения определяет сервер. Присланные одноимённые и любые неизвестные поля верхнего уровня MUST игнорироваться без ошибки и MUST NOT возвращаться в ответе.
- **FR-003**: Принятая заявка MUST получить серверные поля по контракту §5: `id`, `status: 'confirmed'`, `endDate`, `price` (шесть сумм), `createdAt`.

#### Правила проверки полей

- **FR-004**: Проверку полей MUST выполнять чистая функция `validateBooking(payload, today)` из `src/booking.js` — **одна и та же** для UI и сервера (контракт §3). Сервер MUST NOT вводить дополнительных правил на поля сверх неё, а UI MUST NOT ослаблять её у себя.
- **FR-005**: `validateBooking` MUST применять правила полей из контракта §4 (`carId` из `cars`; `days` — целое `MIN_DAYS`…`MAX_DAYS`; `extras` — массив значений `EXTRA_OPTIONS` без повторов, по умолчанию `[]`; `name` — 2–60 символов разрешённого набора; `phone` — по §6; `startDate` — существующая дата от «сегодня» до +`BOOKING_HORIZON_DAYS` включительно) и возвращать по каждому нарушению код из каталога контракта §7.
- **FR-006**: Границы `MIN_DAYS`, `MAX_DAYS`, набор `EXTRA_OPTIONS` MUST импортироваться из `src/calc.js`, а `BOOKING_HORIZON_DAYS` MUST существовать в единственном месте — `src/booking.js` (контракт §2, §3). Числовые границы MUST NOT дублироваться литералами в коде проверки, сервера или текстов.
- **FR-007**: `validateBooking` MUST собирать ошибки по всем полям за один проход, не останавливаясь на первой, и возвращать их в стабильном порядке полей `carId`, `days`, `extras`, `name`, `phone`, `startDate` (контракт §5).
- **FR-008**: Каждая запись об ошибке MUST содержать `field`, `code` из каталога контракта §7 и `message` — человеческую формулировку на русском из `src/`. `message` предназначен для `curl`, логов и тестов API; UI рендерит по `code` и `message` не показывает. Сервер MUST NOT присылать формулировки, предназначенные для показа.
- **FR-009**: Текущая дата MUST передаваться в `validateBooking` параметром; функция MUST NOT обращаться к часам, сети и DOM. К часам обращается только HTTP-обработчик — через `todayUtc()` из `src/booking.js` (контракт §2).
- **FR-010**: Проверка полей MUST выполняться до правила повторной отправки и до проверки занятости; при непройденной проверке ни то, ни другое не выполняется и хранилище не меняется.
- **FR-011**: Нормализацию телефона MUST делать сервер функцией `normalizePhone` из `src/booking.js` по правилу контракта §6; UI присылает телефон как введён.

#### Пересчёт цены

- **FR-012**: Цену MUST считать сервер вызовом `calculateRental({ carId, days, extras })` из существующего `src/calc.js`. Правила расчёта (база, скидки 10 % от 7 суток и 15 % от 14, опции за сутки, страховка 15 % от базы после скидки, залог по классу, округление до рубля) MUST NOT дублироваться в коде заявки, а `src/calc.js` MUST остаться без изменений (контракт §12).
- **FR-013**: `price` в ответе MUST содержать ровно шесть сумм из `calculateRental` в целых рублях; залог в `total` не входит (контракт §5).
- **FR-014**: Цена MUST фиксироваться в хранилище в момент приёма заявки; позднейшее изменение прайса в `src/cars.js` MUST NOT менять цену уже принятых заявок.

#### Повторная отправка

- **FR-015**: Прошедшая проверку заявка, **полностью совпадающая** с уже принятой по ключу контракта §9 (`carId`, `startDate`, `days`, `extras` как множества, `name` после `trim`, `phone` после нормализации), MUST получать `200` с телом существующей заявки, без заголовка `Location`, без создания новой брони и без расхода номера.
- **FR-016**: Правило повторной отправки MUST проверяться **до** правила пересечения дат: точный повтор MUST NOT получать `409`.
- **FR-017**: Несовпадение хотя бы по одному полю ключа MUST трактоваться как новая заявка и проходить обычный путь, включая `409` при пересечении.

#### Пересечение дат

- **FR-018**: Занятый машиной период MUST выражаться полуоткрытым интервалом календарных суток UTC `[startDate, endDate)`, где `endDate` = `startDate` + `days` суток; день `endDate` свободен для новой аренды (контракт §8).
- **FR-019**: Пересечение MUST определяться чистой функцией `overlaps(a, b)` из `src/booking.js` по правилу `aStart < bEnd && bStart < aEnd`; касание встык пересечением не является. Правило действует только в пределах одного `carId`.
- **FR-020**: Новая заявка MUST быть отклонена с `409` `date_conflict`, если пересекается хотя бы с одной принятой заявкой на ту же машину. Тело MUST содержать обязательное поле `conflict` с `carId` и **ISO-датами полуоткрытого интервала**; при нескольких пересечениях называется первый по `startDate`. Имя и телефон из чужой заявки MUST NOT раскрываться.
- **FR-021**: Сервер MUST отдавать границы конфликта в ISO-виде и MUST NOT пересчитывать их в «последний занятый день»: преобразование `addDays(conflict.endDate, -1)` и форматирование через `formatDate` — работа UI (контракт §8).
- **FR-022**: Проверка занятости и запись заявки MUST быть одним неделимым шагом обработки запроса, без `await` между ними, чтобы две одновременные заявки на один интервал не прошли обе.

#### HTTP API

- **FR-023**: Система MUST принимать заявку запросом `POST /api/bookings` с телом JSON; `Content-Type: application/json` обязателен.
- **FR-024**: Успешный приём MUST отвечать `201` с заголовком `Location: /api/bookings/{id}` и телом по контракту §5.
- **FR-025**: Коды ответов, их условия и значения `error.code` MUST соответствовать таблице контракта §5 (`201`, `200`, `400 validation_failed`, `400 invalid_json`, `404 booking_not_found`, `404 not_found`, `405 method_not_allowed` с заголовком `Allow`, `409 date_conflict`, `413 payload_too_large`, `415 unsupported_media_type`, `500 internal_error`). Иных кодов и иных значений `error.code` система вводить MUST NOT.
- **FR-026**: Система MUST отдавать принятую заявку по `GET /api/bookings/{id}`: `200` с телом заявки без `Location` или `404` `booking_not_found`. Других ручек в v1 нет (контракт §5, §12).
- **FR-027**: Тот же процесс MUST отдавать `GET /` и статические файлы (`index.html`, `styles.css`, `src/**`) на порту 8000 (контракт §1). Путь, начинающийся с `/api/`, MUST NOT обслуживаться как файл; файлы за пределами корня проекта MUST NOT читаться.
- **FR-028**: Любой ответ с телом MUST иметь `Content-Type: application/json; charset=utf-8` (кроме статики, которой тип соответствует файлу); тело ошибки MUST иметь единую форму контракта §5 с массивом `fields` всегда. HTML и стектрейсы MUST NOT отдаваться.
- **FR-029**: Непредвиденный сбой MUST отвечать `500` `internal_error` без внутренних подробностей; процесс MUST продолжать обслуживать следующие запросы.
- **FR-030**: Тело больше 8 КБ MUST NOT разбираться (`413`); нераспознанное тело, включая пустое, MUST давать `400 invalid_json`.
- **FR-031**: Сервер MUST отвечать на любой запрос за ≤ 2 с (контракт §10). CORS-заголовки и обработка `OPTIONS` в v1 MUST NOT вводиться: UI и API на одном источнике.

#### Хранение

- **FR-032**: Заявки MUST храниться в памяти процесса; база данных, файлы и внешние сервисы MUST NOT использоваться (контракт §11).
- **FR-033**: Номер заявки MUST быть уникальным, выдаваться последовательно, не переиспользоваться в пределах жизни процесса и иметь формат контракта §5 (`AD-` + не менее 4 цифр с ведущими нулями). Отклонённая заявка и повторная отправка номер MUST NOT расходовать.
- **FR-034**: `src/booking-store.js` MUST предоставлять операции контракта §3 и §11: `add`, `findById`, `findSame` (ключ §9), `intervalsFor`, `clear` (последняя — для тестов).
- **FR-035**: Перезапуск процесса MUST оставлять хранилище пустым и начинать нумерацию с `AD-0001`; это ограничение MUST быть зафиксировано как принятое, а не исправляться файловым хранением.
- **FR-036**: Логика проверки, дат, цены и хранения MUST лежать в `src/` как функции без обращения к сети, DOM и часам (текущая дата параметром) и MUST быть покрыта тестами `node --test`; HTTP-слой MUST жить отдельно в `server.js` в корне и использовать только встроенные модули Node 24 (контракт §1, §13).
- **FR-037**: Тесты MUST покрывать каждую строку каталога контракта §7, правила §8 и §9 и каждую строку таблиц раздела «Граничные значения»; `sh scripts/check.sh` MUST оставаться зелёным, а ранее принятые сценарии лендинга, калькулятора и фильтра — выполненными (контракт §13).
- **FR-038**: Формулировки, которые видит посетитель, MUST жить в `src/booking-text.js` (объём UI); серверная сторона MUST NOT дублировать их у себя и MUST NOT присылать в ответе.

### Key Entities

- **Заявка на бронирование (Booking)**: что посетитель просит и что сервер решил. Поля — по контракту §4 (от UI) и §5 (от сервера). Привязана к одной машине автопарка; живёт в памяти процесса.
- **Занятый интервал (BusyInterval)**: проекция заявки на календарь одной машины — полуоткрытая пара дат (контракт §8). Единица, на которой работает `overlaps`.
- **Ключ повторной отправки (SameKey)**: набор полей из контракта §9, по которому заявка узнаётся как уже принятая. `extras` в нём сравниваются как множества.
- **Разбор ошибок проверки (ValidationFailure)**: список записей `{ field, code, message }`, стабильно упорядоченный по полям. Коды — только из каталога контракта §7.
- **Машина автопарка (Car)**: существующая сущность из `src/cars.js`. Эта фича её читает и не меняет.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Посетитель, закончивший расчёт, получает номер заявки, отправив ровно три дополнительных поля (имя, телефон, дата начала) — срок и опции переносятся из снимка расчёта без повторного ввода.
- **SC-002**: Цена в ответе совпадает с итогом калькулятора для тех же машины, срока и опций в 100 % случаев: обе стороны считают одним `calculateRental`, и строка об уточнении итога в UI не появляется ни в одном сценарии приёмки.
- **SC-003**: Ни одна машина ни при одном сценарии приёмки не оказывается занята двумя разными заявками на пересекающиеся сутки; при пересечении посетитель узнаёт занятый интервал и может выбрать другие даты.
- **SC-004**: Повторное нажатие кнопки после потери ответа не создаёт вторую бронь и не приводит к отказу «машина занята»: число записей в хранилище после N идентичных отправок равно 1.
- **SC-005**: По каждому отклонённому полю посетитель получает одно сообщение, называющее, что исправить; все 16 кодов полей из каталога контракта §7 достижимы хотя бы одним сценарием приёмки.
- **SC-006**: Отклонённая заявка не оставляет следа: число принятых заявок после любой серии отказов равно числу успехов, а номера не расходуются.
- **SC-007**: Любой запрос к API — корректный, ошибочный или бессмысленный — получает ответ в единой форме JSON за ≤ 2 с; процесс не падает и продолжает обслуживать запросы.
- **SC-008**: Ни одно имя поля, ни один код и ни одна видимая формулировка не существуют вне контракта и модулей `src/`: при изменении кода или текста правка делается в одном месте.
- **SC-009**: Логика заявки не копирует правила расчёта: при изменении цены или порога скидки в `src/calc.js` ответы API меняются без правок в коде заявки.
- **SC-010**: `sh scripts/check.sh` зелёный; тесты покрывают каждую строку каталога контракта §7, правила §8 и §9 и все таблицы раздела «Граничные значения»; сценарии ранее принятых фич A, B и C остаются выполненными.

## Assumptions

Решения, ранее бывшие предположениями этой спецификации, теперь закреплены контрактом и здесь
не повторяются (UTC и «сегодня» — §2, горизонт 365 — §2, формат телефона — §6, единственный
статус `confirmed` — §12, объём хранилища — §12, один origin — §1). Остаётся:

- **Переиспользование `src/calc.js` без правок.** Правила расчёта, границы `MIN_DAYS`/`MAX_DAYS` и набор `EXTRA_OPTIONS` берутся из существующего модуля (контракт §12). Если приёмка потребует иной скидки или опции, это правка фичи B и отдельное изменение контракта.
- **Проверка полей — один предикат на обе стороны.** Этим исключается расхождение «UI считает валидным, сервер — нет» для всех полей, кроме зависящих от состояния сервера (`date_conflict`). Цена предположения: `src/booking.js` импортируется и в браузер, и в Node, поэтому в нём нет ни `node:`-импортов, ни обращений к DOM.
- **`GET /api/bookings/{id}` без авторизации.** Допустимо только потому, что данные вымышленные, а хранилище живёт в памяти демо-процесса (контракт §5).
- **Правки `package.json` и `docs/requirements.md` разрешены владельцем** и делаются на этапе реализации: `scripts.start` запускает сервер Node вместо `python3 -m http.server`, в требования добавляется «Фича D: заявка на бронирование» со ссылкой на контракт (контракт §1). Эта спецификация их не меняет.
- **Статика отдаётся простым сопоставлением пути с файлом** без кэш-заголовков, диапазонных запросов и сжатия: задача — открыть лендинг с того же порта, а не заменить веб-сервер.
- **Нагрузка — демонстрационная.** Один посетитель и единицы заявок; защита от конкурентных заявок строится на однопоточности обработчика (FR-022), а не на блокировках.
