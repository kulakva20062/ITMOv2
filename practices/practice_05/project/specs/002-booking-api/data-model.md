## Booking — заявка в хранилище

Одна запись = одна принятая заявка. Хранится как обычный объект, который сериализуется в
тело ответа **без преобразования**: форма записи совпадает с формой ответа контракта §5,
поэтому обработчику не нужен маппер.

| Поле | Тип | Источник | Правило |
|---|---|---|---|
| `id` | строка | хранилище | `AD-` + счётчик, ≥ 4 цифры с ведущими нулями |
| `status` | строка | сервер | всегда `'confirmed'` — других статусов в v1 нет (контракт §12) |
| `carId` | строка | запрос | `id` из `cars`; связь с машиной — по значению, копии данных машины не храним |
| `startDate` | строка `YYYY-MM-DD` | запрос | проверенная календарная дата |
| `endDate` | строка `YYYY-MM-DD` | сервер | `addDays(startDate, days)` — исключительная граница (контракт §8) |
| `days` | целое | запрос | 1…30 |
| `extras` | массив строк | запрос, переупорядочен | отсортирован по порядку `EXTRA_OPTIONS`, без повторов |
| `customer.name` | строка | запрос | после `trim`, регистр как ввёл посетитель |
| `customer.phone` | строка | запрос, нормализован | `+7XXXXXXXXXX` |
| `price` | объект из 6 чисел | `calculateRental` | `base`, `discount`, `extrasTotal`, `insurance`, `total`, `deposit`; целые рубли |
| `createdAt` | строка ISO | сервер (параметр `now`) | момент приёма |

**Инварианты**:

1. `endDate` строго больше `startDate` (следует из `days ≥ 1`).
2. `price` — снимок на момент приёма: пересчёт при чтении не делается никогда (FR-014).
3. `extras` в записи уже канонизированы, поэтому сравнение по ключу §9 и вывод в ответ не
   требуют повторной сортировки.
4. Запись неизменяема после `add`: отмены и правки вне объёма v1, поэтому мутаций нет.
5. Поля с ценой, номером и датами никогда не приходят от клиента — они проставляются только
   внутри `add` и обработчика (FR-002).

**Что в записи не хранится**: данные машины (модель, класс, прайс) — они берутся из
`src/cars.js` по `carId`; это не даёт устареть автопарку и не дублирует источник.

## BusyInterval — занятый интервал

Проекция заявки на календарь одной машины: `{ startDate, endDate }`, полуоткрытый
`[startDate, endDate)` (контракт §8). Отдельной сущности в памяти нет — `intervalsFor(carId)`
строит интервалы из заявок на лету.

**Инварианты**:

1. Интервалы одной машины попарно не пересекаются — это и есть главный инвариант фичи,
   поддерживаемый проверкой перед `add`.
2. Касание встык (`aEnd === bStart`) допустимо и встречается в нормальной работе.
3. Сортировка — по `startDate` по возрастанию: нужна, чтобы в `conflict` попадал первый
   пересекающийся интервал (FR-020).
4. Интервалы разных `carId` независимы.

## SameKey — ключ повторной отправки

Набор полей из контракта §9, по которому заявка узнаётся как уже принятая:
`carId`, `startDate`, `days`, `extras` (как множество), `name` после `trim`,
`phone` после нормализации.

**Инварианты**:

1. Ключ считается по нормализованным значениям (R-12), то есть по тем, что сохранены в записи.
2`.` Ключ не включает `price`, `id`, `createdAt`, `endDate` — они производные и совпадут автоматически.
3. Совпадение ключа → возврат существующей записи; расхождение хотя бы в одном поле → новая заявка.

## ValidationFailure — разбор ошибок проверки

Результат `validateBooking`: список записей `{ field, code, message }` плюс нормализованные
значения для успешного случая.

**Инварианты**:

1. Порядок записей — `carId`, `days`, `extras`, `name`, `phone`, `startDate` (контракт §5).
2. На одно поле — не больше одной записи: коды по полю взаимоисключающи и проверяются в
   фиксированном порядке (например для `name`: `required` → `name_length` → `name_charset`).
3. Все `code` — из каталога контракта §7; новых кодов не вводится.
4. Пустой список ошибок означает, что `calculateRental` вызывать безопасно (FR-016, R-14).

## Store — хранилище в памяти

Состояние: массив заявок (порядок добавления) и числовой счётчик номеров.

| Операция | Что делает | Побочный эффект |
|---|---|---|
| `add(booking)` | присваивает `id`, кладёт запись | инкремент счётчика |
| `findById(id)` | запись или `undefined` | нет |
| `findSame(key)` | запись с совпадающим ключом §9 или `undefined` | нет |
| `intervalsFor(carId)` | интервалы машины, отсортированные по `startDate` | нет |
| `clear()` | опустошает массив и сбрасывает счётчик | только для тестов |

**Инварианты**:

1. Счётчик растёт только в `add` — отказ и повтор номер не расходуют (FR-033).
2. `clear()` возвращает хранилище в состояние «после старта процесса»: нумерация снова с `AD-0001`.
3. Состояние живёт только в памяти; перезапуск — пустое хранилище (FR-032, FR-035).
4. Операции синхронные — это условие неделимости «проверил → записал» (R-09).

## Car — машина автопарка

Существующая сущность `src/cars.js` (`id`, `model`, `class`, `gearbox`, `seats`, `pricePerDay`).
Фича только читает её: для проверки `carId` и внутри `calculateRental`. Изменений нет.

## Фикстуры для тестов

Только вымышленные данные (принцип IV). Эти значения используются в `tests/booking.test.js`,
`tests/booking-store.test.js`, `tests/server.test.js` и в [quickstart.md](./quickstart.md).

**Корректная заявка** (`larus-16`, 2400 ₽/сутки, класс `economy`):

```json
{
  "carId": "larus-16",
  "days": 3,
  "extras": [],
  "name": "Иван Петров",
  "phone": "+7 000 000-00-00",
  "startDate": "2026-11-10"
}
```

Ожидаемое: `endDate 2026-11-13`, `price { base 7200, discount 0, extrasTotal 0, insurance 0, total 7200, deposit 10000 }`,
`customer.phone "+70000000000"`.

**Та же заявка с опциями** `["child-seat","full-insurance"]`:
`extrasTotal 900`, `insurance 1080`, `total 9180` (пример контракта §5).

**Фиксированные часы тестов**: `today = '2026-10-23'`, `now = '2026-10-23T12:00:00.000Z'`.
Отсюда границы: `date_past` ← `2026-10-22`, верхняя граница горизонта ← `2027-10-23`,
`date_too_far` ← `2027-10-24`.

**Машины для проверки независимости по `carId`**: `larus-16` (economy, 2400) и
`prima-sedan` (business, 7200, залог 30000).

**Телефонные варианты одной и той же нормализации** (для ключа §9):
`"+7 000 000-00-00"`, `"80000000000"`, `"+7 (000) 000-00-00"` → `+70000000000`.
