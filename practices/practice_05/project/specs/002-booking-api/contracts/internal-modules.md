# Внутренние контракты модулей — booking-api

**Дата**: 2026-10-23 · **Внешний контракт**: [`specs/contracts/booking-contract.md`](../../contracts/booking-contract.md) §3

Контракт §3 называет экспорты по именам; здесь зафиксировано, что каждая функция принимает и
что возвращает. Имена полей результата, кроме служебных (`ok`, `errors`, `value`), — те же,
что в контракте. Реализация в этом файле не описывается: только границы.

---

## `src/booking.js` — чистые функции, работают и в браузере, и в Node

Модуль **не содержит** `node:`-импортов и обращений к DOM: контракт §3 требует одного
предиката на обе стороны. Импортирует `cars` из `./cars.js` и `MIN_DAYS`, `MAX_DAYS`,
`EXTRA_OPTIONS` из `./calc.js`.

### Константы

| Экспорт | Тип | Значение |
|---|---|---|
| `BOOKING_HORIZON_DAYS` | число | `365` — единственное место, где живёт горизонт (контракт §2) |
| `ERROR_CODES` | замороженный объект | все 16 кодов полей каталога §7 как `{ REQUIRED: 'required', … }`; единственный источник строк кодов для кода и тестов |

### `todayUtc() -> string`

Сегодняшняя дата UTC в виде `'YYYY-MM-DD'` (контракт §2). **Единственный аксессор часов в
`src/`**; вся остальная логика получает дату параметром. Вызывается только обработчиком
запроса и обработчиком отправки формы.

### `addDays(iso, n) -> string`

`iso` — `'YYYY-MM-DD'`, `n` — целое (может быть отрицательным). Возвращает ISO-дату,
сдвинутую на `n` календарных суток UTC. Используется для `endDate` (`n = days`), для верхней
границы горизонта и для «последнего занятого дня» (`n = -1`, контракт §8).
На невалидном `iso` бросает `RangeError` — это признак дефекта вызывающего, а не ввода.

### `isValidName(value) -> boolean`

`true`, если `value` после `trim` проходит правило имени контракта §4: 2…60 кодовых точек,
только буквы кириллицы/латиницы, пробел, дефис, апостроф, и хотя бы одна буква.
Предикат без диагностики — коды различает `validateBooking`.

### `normalizePhone(value) -> string | null`

Нормализация по правилу контракта §6: `'+7 000 000-00-00'` → `'+70000000000'`.
Возвращает `null`, если нормализация невозможна (не те символы, не 11 цифр, не код `7`/`8`).
Различение `phone_charset` и `phone_invalid` — задача `validateBooking`.

### `validateBooking(payload, today) -> ValidationResult`

Проверяет тело запроса по правилам контракта §4 и §6. `today` — `'YYYY-MM-DD'`,
обязательный параметр; к часам функция не обращается (принцип II).

Успех:

```js
{
  ok: true,
  errors: [],
  value: {
    carId, days, extras,          // extras канонизированы по порядку EXTRA_OPTIONS
    name,                         // после trim
    phone,                        // нормализованный +7XXXXXXXXXX
    startDate,
    endDate                       // addDays(startDate, days)
  }
}
```

Отказ:

```js
{
  ok: false,
  errors: [ { field: 'days', code: 'days_out_of_range', message: '…' }, … ],
  value: null
}
```

Правила результата:

- `errors` упорядочены по полям `carId`, `days`, `extras`, `name`, `phone`, `startDate` (контракт §5).
- На одно поле — не больше одной записи; коды по полю взаимоисключающи.
- Все `code` — значения из `ERROR_CODES`.
- `message` — формулировка для `curl`, логов и тестов API; UI её не показывает (контракт §5, решение R-08).
- Отсутствующий `extras` трактуется как `[]`; `payload`, не являющийся объектом, — ответственность вызывающего (обработчик отдаёт `invalid_json` раньше).

### `overlaps(a, b) -> boolean`

`a`, `b` — `{ startDate, endDate }`. Возвращает `true` по правилу контракта §8
`aStart < bEnd && bStart < aEnd`. `carId` функция не знает — фильтрацию по машине делает
вызывающий через `intervalsFor`.

## `src/booking-store.js` — состояние в памяти

Импортирует только `src/booking.js` (для сравнения ключа §9). Без `node:`-импортов —
чтобы модуль оставался тестируемым напрямую. Все операции **синхронные**: это условие
неделимости «проверил занятость → записал» (решение R-09).

### `createStore() -> Store`

Новый независимый экземпляр хранилища. Тесты создают свой, чтобы не зависеть от порядка
исполнения.

### Экземпляр по умолчанию

Модуль экспортирует общий экземпляр для `server.js`, запущенного как процесс.

### Операции `Store`

| Операция | Принимает | Возвращает | Побочный эффект |
|---|---|---|---|
| `add(draft, now)` | заготовку заявки (результат `validateBooking().value` + `price`) и ISO-момент | готовую запись с `id`, `status: 'confirmed'`, `createdAt` | кладёт запись, инкрементирует счётчик |
| `findById(id)` | номер заявки | запись или `undefined` | нет |
| `findSame(key)` | нормализованные поля ключа §9 | запись или `undefined` | нет |
| `intervalsFor(carId)` | `carId` | массив `{ startDate, endDate }`, отсортированный по `startDate` | нет |
| `clear()` | — | — | опустошает массив, сбрасывает счётчик (только для тестов) |

- `id` формируется как `AD-` + счётчик с `padStart(4, '0')` (контракт §5).
- Счётчик растёт **только** в `add`: отказы и повторные отправки номер не расходуют.
- Запись, которую отдаёт `add`, по форме совпадает с телом ответа `201` — маппер не нужен
  (см. [data-model.md](../data-model.md)).

## `server.js` — HTTP-слой в корне

Использует `node:http`, `node:fs`, `node:path`, `node:url`. Логику не содержит: только
роутинг, чтение тела, коды ответов и сборка тел по контракту §5.

### `createBookingServer(options) -> http.Server`

| Опция | По умолчанию | Зачем |
|---|---|---|
| `store` | общий экземпляр из `booking-store.js` | тесты передают свой |
| `today` | `todayUtc` | тесты фиксируют дату — проверяемость `date_past` / `date_too_far` |
| `now` | `() => new Date().toISOString()` | тесты фиксируют `createdAt` |
| `root` | корень проекта | откуда отдаётся статика |

Возвращает **не слушающий** `http.Server`. Прослушивание порта 8000 — только при прямом
запуске файла; тесты делают `listen(0)` и читают выданный порт (решение R-01).

### Маршруты

| Метод и путь | Поведение |
|---|---|
| `POST /api/bookings` | порядок проверок — решение R-03; ответы `201` / `200` / `400` / `409` / `413` / `415` / `500` |
| `GET /api/bookings/{id}` | `200` с телом записи без `Location`, либо `404 booking_not_found` |
| другой метод на известном пути `/api/**` | `405 method_not_allowed` + заголовок `Allow` |
| другой путь `/api/**` | `404 not_found` |
| `GET /` | `index.html` |
| `GET /<файл>` | статика от корня проекта; выход за корень запрещён (решение R-05) |

Пути, начинающиеся с `/api/`, никогда не обслуживаются как файлы. CORS-заголовков и
обработки `OPTIONS` нет (контракт §12).

### Форма ответов

Собирается ровно по контракту §5: тело ошибки — `{ error: { code, message, fields } }`,
`fields` — массив всегда, у `409` дополнительно обязательное `conflict` с ISO-датами
полуоткрытого интервала. `Content-Type: application/json; charset=utf-8` у всех ответов API;
у статики — тип по расширению файла.
