# AutoDrive Constitution

## Core Principles

### I. Чистый стек без зависимостей (NON-NEGOTIABLE)

Лендинг пишется на чистых HTML, CSS и JavaScript (ES-модули). Фреймворки, сборщики,
транспиляторы и npm-зависимости запрещены: `package.json` остаётся без блоков
`dependencies` и `devDependencies`. Если появляется серверный код, он использует только
встроенные модули Node 24 — внешние пакеты не подключаются и там. Тестовый раннер — тоже
встроенный: `node --test`.

Обоснование: проект должен открываться и проверяться на чистой машине с одним Node 24,
без установки чего-либо. Любая зависимость ломает это свойство.

### II. Логика — чистые функции в `src/` под тестами

Любой расчёт, отбор или форматирование живёт в `src/` как чистая функция: результат
определяется только аргументами, без обращения к DOM, времени, случайности и сети.
Каждая такая функция покрывается тестами в `tests/` через свой публичный экспорт, а
поведение страницы проверяется через экспортируемые функции и разметку `index.html`.
Разметку, подписи и сообщения, которые нужны и UI, и тестам, дают чистые функции или
константы из тех же модулей `src/` — UI их не дублирует строками.

Обоснование: чистые функции — единственная часть проекта, которую можно проверить
дёшево и однозначно; всё, что утекло в обработчики DOM, перестаёт быть проверяемым.

### III. Зелёный `scripts/check.sh` после каждой правки (NON-NEGOTIABLE)

`sh scripts/check.sh` — единственный раннер проекта, и он MUST проходить после каждой
правки, а не только перед сдачей. Правка считается незавершённой, пока раннер красный.
Ослаблять, пропускать или обходить проверку, чтобы получить зелёный результат,
запрещено (см. раздел «Рабочий процесс и приёмка»).

Обоснование: проверка после каждого шага локализует поломку в одной правке; проверка
раз в конце превращает отладку в поиск среди всех изменений.

### IV. Только вымышленные данные, никаких внешних ресурсов

Все данные вымышлены: никаких реальных адресов, телефонов, e-mail и брендов прокатов.
Заглушки фиксированы: `+7 000 000-00-00` и `hello@example.com`. Внешние CDN, шрифты и
картинки из сети не подключаются: в `src`/`href` допустимы только относительные пути и
`#`, изображения делаются средствами CSS или inline SVG, шрифты — только локальные стеки
из `styles.css`.

Обоснование: страница обязана работать и проверяться без сети, а вымышленные данные
исключают случайное упоминание реального бизнеса или живого контакта.

### V. Контракт до кода — единственный источник имён (NON-NEGOTIABLE)

Команда UI и команда логики согласуют общий контракт до написания кода. Контракт —
единственный источник имён полей, кодов (типов) ошибок и состояний: имена аргументов и
полей ответа чистых функций, тексты и классы ошибок, значения и подписи состояний
интерфейса. Ни UI, ни логика не вводят своё имя поля, своё состояние или свой код
ошибки в обход контракта и не выводят их заново из кода другой стороны. Изменение
контракта — отдельный согласованный шаг обеих команд до правки кода; код, разошедшийся
с контрактом, правится по контракту, а не наоборот.

Обоснование: две команды, работающие параллельно, расходятся именно на именах и
состояниях. Один письменный источник делает расхождение видимым до кода, а не после
интеграции.

## Визуальные и технические ограничения

`docs/style-guide.md` MUST быть прочитан перед любой правкой вёрстки и обязателен к
исполнению:

- Визуальный язык — приёмо-сдаточный лист осмотра: бумага, волосяные линии, подписи
  полей в левой рейке. Новые блоки продолжают этот язык, а не вводят карточки с тенями.
- Цвета — только токены `:root`: `--paper`, `--ink`, `--ink-2`, `--rule`, `--signal`,
  `--stamp`. Новые цвета не добавляются. `--stamp` — только ошибки ввода. Пары
  текст/фон проходят WCAG AA (4.5:1 для обычного текста).
- Без теней и градиентов; `border-radius` 0 у полей и строк, 2px у кнопок.
- Цифры в ценах — `font-variant-numeric: tabular-nums`; суммы выводятся только через
  `formatPrice` из `src/format.js`.
- Ошибка ввода — текст цветом `--stamp` рядом с полем, с `role="alert"`; формулировка
  говорит, что исправить, без извинений.
- Анимация на странице одна (заливка кузова в hero); всё новое — без анимации,
  `prefers-reduced-motion` уважается.

Перед работой также читаются `docs/requirements.md` (требования и фичи A/B/C) и
`tests/format.test.js` как пример теста.

## Рабочий процесс и приёмка

- Контракт в `docs/requirements.md`, `scripts/check.sh` и существующие тесты
  не ослабляются и не переписываются ради зелёного результата без отдельного поручения.
  Если код не сходится с требованиями — правится код.
- Новая логика идёт вместе с тестами в той же правке; критерии приёмки соответствующей
  фичи из `docs/requirements.md` — минимум покрытия, а не пожелание.
- Сценарии ранее принятых фич MUST сохраняться: новая фича не ломает критерии
  приёмки предыдущих.
- Коммит делает студент после приёмки. Агент не коммитит и не пушит.

## Governance

Эта конституция имеет приоритет над привычками и локальными решениями в коде. Источники
её правил — `AGENTS.md` и `docs/style-guide.md`; при расхождении текста конституции с
этими файлами расхождение считается дефектом и устраняется отдельной поправкой, а не
молчаливым выбором одной из версий.

Поправки: изменение вносится в этот файл отдельным шагом, с обновлением версии, даты
последней правки и Sync Impact Report. Поправка, меняющая правило работы двух команд
(принцип V), требует согласия обеих команд. Правила, затрагивающие контракт
`docs/requirements.md`, меняются только по поручению владельца проекта.

Версионирование: семантическое. MAJOR — удаление или несовместимое переопределение
принципа; MINOR — новый принцип или материально расширенное правило; PATCH — уточнение
формулировок без смены смысла.

Соответствие: каждая правка проверяется зелёным `sh scripts/check.sh` (принцип III) и
соответствием `docs/style-guide.md` для вёрстки. Отступление от принципа допустимо
только как явно зафиксированная поправка к этому файлу. Оперативные указания для работы
в репозитории — в `AGENTS.md`.
