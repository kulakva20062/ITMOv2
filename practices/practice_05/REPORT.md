# Практика 5: SDD в существующем проекте

Brownfield-проект — лендинг проката AutoDrive из практики 4 (ветка `2026_Kulakovskii_Vlad_practies_4`, коммит `a80c913`), скопирован в `project/`. До начала работы в нём было 66 зелёных тестов.

Агент — Claude Code, как у ведущего на занятии. Каждый шаг выполнялся отдельной сессией `claude -p` в `project/`. Модель `claude-opus-5`: установленный CLI 2.1.223 не поддерживает Opus 5.5. «Отдельный чат» со слайдов означает новую сессию без контекста автора. Решения человека записаны в промптах. Лог каждой сессии лежит в `evidence/*.md`: промпт, id сессии, список вызовов инструментов и ответ агента.

Запуск из этой папки:

```sh
make test    # 257 тестов: фичи A–D
make run     # http://localhost:8000/ — лендинг и API заявок
make specs   # состояние OpenSpec
```

## Домашняя работа: две команды, одна фича (Spec Kit)

Другой SDD-фреймворк — **GitHub Spec Kit** (`specify-cli` 1.2.4.dev0, `specify init --here --integration claude --script sh`). Без расширения `git` он не создаёт веток и пишет фичи в `specs/NNN-*`.

Фича: **заявка на бронирование**. После расчёта посетитель оставляет имя, телефон и дату. Сервер проверяет заявку, сам пересчитывает цену, не даёт забронировать одну машину на пересекающиеся даты и отвечает номером `AD-NNNN`.

### Что согласовали (главное из 15 решений)

- **Один origin.** `node server.js` отдаёт и страницу, и `/api` на порту 8000, поэтому CORS не нужен. `package.json` и «Фича D» в `docs/requirements.md` обновлены с разрешения владельца.
- **Одна проверка на обе стороны.** UI вызывает тот же `validateBooking(payload, today)`, что и сервер, поэтому ситуация «UI считает поле верным, а сервер нет» невозможна, кроме конфликта дат.
- **UI рендерит ошибки по `code`, а не по `message`.** `message` остаётся в API для curl и тестов. Каталог `code → поле → состояние UI → текст` записан в §7 контракта.
- **Интервал полуоткрытый `[start, end)`.** День возврата свободен. UI показывает последний занятый день как `endDate − 1`; иначе текст ошибки противоречил бы тому, что заявка встык проходит.
- **«Сегодня» считается в UTC с обеих сторон.** Горизонт бронирования — `BOOKING_HORIZON_DAYS = 365` в одном месте.
- **Повтор идентичной заявки возвращает `200` с той же заявкой.** Это закрывает сценарий «ответ потерялся, посетитель нажал ещё раз».
- **5xx и таймаут (10 с) переводят форму в «сервер недоступен».** Ошибки по `carId`, `days` и `extras` дают «Расчёт устарел…» и возвращают форму в «нет расчёта».
- Во время реализации UI в §7 добавлены машиночитаемые имена состояний (`no-estimate`, `editing`, `submitting`, `success`, `unavailable`). Правку внёс владелец, код не писался до неё.

## Сравнение Spec Kit и OpenSpec

| | OpenSpec (часть 1–2) | Spec Kit (ДЗ) |
|---|---|---|
| Единица работы | change — дельта (ADDED/MODIFIED) к живой спеке системы; после archive она вливается в `openspec/specs/` | feature-каталог `specs/NNN-*` с полной спекой фичи; общей «текущей спеки системы» нет, sync/archive тоже нет |
| Brownfield | естественно: вторая фича (`fleet-filter-reset`) добавила к `fleet-filtering` 4 ADDED- и 2 MODIFIED-требования | состояние проекта передаётся через constitution и чтение кода, а связь фич — вручную (общий контракт пришлось заводить самим) |
| Объём артефактов | ~290 строк на фичу (proposal, spec, design, tasks), 21 задача | ~1300–1600 строк на фичу (spec, plan, research, data-model, contracts, quickstart, tasks, checklist), 36 и 54 задачи |
| Проверка документов | детерминированный CLI: `openspec validate --strict`, `status`, `instructions` | CLI только создаёт каркас; качество спеки оценивает модель по чек-листу (`/speckit-analyze` опционален) |
| Правила проекта | `config.yaml` → `rules.<артефакт>`; CLI подставляет их в инструкции, что видно в `openspec instructions … --json` | `constitution.md` плюс раздел Constitution Check в каждом plan |
| Параллельная работа | несколько активных changes одновременно, каждый в своей папке | один общий `.specify/feature.json`: команда 2 переписала указатель команды 1, и команде 1 пришлось выставлять его заново |
| Время и стоимость в этой практике | 2 фичи (одна до archive, одна draft): ~32 мин работы агента, ~$24 | 1 фича двумя командами: ~105 мин, ~$68 |

Вывод: OpenSpec легче и лучше подходит для brownfield, потому что изменение описывается дельтой к уже принятому поведению, а структуру документов проверяет CLI. Spec Kit тяжелее, но его plan, research и quickstart сами превратились в план проверки. Для двух команд ни один фреймворк не даёт общий контракт из коробки, его пришлось вводить принципом конституции и отдельным файлом.

## Отклонения и ограничения

- Модель — `claude-opus-5`, а не Opus 5.5: установленный CLI (2.1.223) его не поддерживает.
- Сессии несколько раз упирались в лимит подписки (сессионный и недельный). Прерванные сессии продолжены через `--resume` той же сессии; в логах это видно.
- Хук `check-after-edit` из практики 4 в логах `stream-json` не виден. Workspace не помечен как доверенный, и CLI пишет, что игнорирует `permissions.allow` проекта; срабатывали ли хуки, по логам не подтвердить. `sh scripts/check.sh` агенты запускали сами, итог подтверждён независимыми прогонами.
- На 360 px подпись «Любая коробка» упирается в стрелку селекта. Спеку это не нарушает; принято как известное замечание.
