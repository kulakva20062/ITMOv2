# Рефлексия: практика 5 и ДЗ

**Что согласовали.** Самое ценное вышло из таблицы расхождений между командами. Обе спеки были написаны аккуратно, но, например, команда UI заложила горизонт бронирования 180 дней, а команда логики — 365. UI собирался писать «занята с 10 по 13 ноября», а для API 13 ноября — свободный день возврата. При раздельной реализации это всплыло бы только на приёмке как «баг»: заявка на 13-е проходит, хотя экран говорит, что машина занята. Ещё одна тихая ловушка — часовой пояс. UI неявно считал «сегодня» по локальному времени, сервер — по UTC. Расхождений было 15, и все решаются за минуту, если их увидеть до кода.

**Чему научился.** Контракт между командами — отдельный документ, а не раздел одной из спек. Пока имена полей, коды ошибок и состояния жили в двух спеках, каждая команда «своими словами» вводила свои имена. После того как в конституции появился принцип «контракт — единственный источник имён», обе спеки стали ссылаться на §7 вместо того, чтобы копировать таблицы. Правку контракта по ходу реализации (имена состояний UI) я внёс сам как владелец до того, как UI начал писать код, и ничего не разъехалось.

**Где пришлось вмешаться.**
- Ревьюер OpenSpec поймал, что все проверки «не тронуто» в tasks написаны через `git diff`, а проект не отслеживается git, так что проверка ничего не доказывает. Базой для сравнения я назначил коммит практики 4.
- Explore сам нашёл, что `<input>` в автопарке сломает тесты калькулятора. Без этого apply упёрся бы в красные тесты, а агенту запрещено менять существующие.
- Spec Kit хранит текущую фичу в одном файле `.specify/feature.json`. Вторая команда переписала указатель первой, и при параллельной работе в одной копии это мешает.
- Агенты несколько раз писали «hook держал раннер зелёным», но в логах следов хука нет. Я поверил только независимым прогонам `check.sh`, а не отчёту автора, как и советовал ведущий.
- Лимиты подписки прерывали длинные `implement` посреди работы. Продолжение через `--resume` той же сессии работает, но агенту приходится заново сверять, что уже сделано: после обрыва ни одна задача не была отмечена, хотя часть кода уже была написана.

**OpenSpec против Spec Kit.** Для существующего проекта мне ближе OpenSpec. Изменение — это дельта к принятому поведению, CLI сам проверяет структуру, а после archive остаётся одна актуальная спека системы. Spec Kit на одну фичу выдал в 5–6 раз больше текста. Но его quickstart и research оказались полезными: по ним отдельный проверяющий шёл без подсказок. Сам SDD окупается там, где работают несколько исполнителей. Для одиночной фичи вроде фильтра хватило бы explore и хорошего промпта, а вот для двух команд согласование до кода сэкономило больше, чем стоило.
