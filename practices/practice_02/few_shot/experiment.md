# Few-shot

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: [`../../practice_01/adr.md`](../../practice_01/adr.md), раздел «Рассмотренные альтернативы» — таблица из семи строк одного формата «Альтернатива | Почему не выбрали сейчас». Выбран потому, что это самый длинный набор однотипных элементов в Практике 1, заполненный заметно неровно: часть ячеек колонки «Почему не выбрали сейчас» построена по полной схеме (отказ привязан к источнику, назван наблюдаемый эффект отказа и указано условие возврата к вопросу), часть — по усечённой (одна ссылка на правило без эффекта и без условия возврата). Именно здесь показ пары «хороший элемент / плохой элемент» задаёт образец, к которому приводятся остальные строки, и задаёт форму для альтернатив, которые добавят позже.
- Что хотим улучшить: привести все семь ячеек колонки «Почему не выбрали сейчас» к одной форме. Наблюдаемый дефект — три расхождения между соседними строками одной таблицы.

  Расхождение 1, условие пересмотра решения есть только у двух строк из семи. Полная форма: «Ни одна строка хунков и ни одно правило из SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1 не требует смены модели исполнения; таймаут 10 секунд по REL-1 ограничивает удержание потока сверху и закрывает наблюдаемую проблему. Возврат к вопросу — при появлении подтверждённого профиля трафика (сейчас его нет, см. [`tests_load.md`](tests_load.md))». Усечённая форма в соседней строке: «OUT-1 прямо задаёт максимум три элемента; выдача большего списка нарушает правило» — статус решения не указан, из ячейки не видно, окончателен отказ или пересматривается при появлении данных.

  Расхождение 2, глубина привязки к источнику разная. Первая строка опирается и на правила, и на дословную цитату из хунка: «Расходится сразу с четырьмя правилами: API-1 (нет проверки длины), REL-1 (нет таймаута и `try/except`), OUT-1 (одно поле вместо трёх), SEC-1 (дифф уходит дословно). Тело `{}` при этом остаётся падением на `KeyError`». Строка «Не ограничивать `risks` тремя элементами, отдавать весь список» не содержит ни одной цитаты из хунков, хотя наблюдаемая отправная точка для неё есть — `return {"comment": answer}` в хунке `app/review_service.py @@ -1,10 +1,23 @@`.

  Расхождение 3, у части строк назван наблюдаемый эффект отказа, у части — нет. Есть: «Клиент перестаёт отличать превышение 20 000 символов от некорректного тела»; «молчаливая обрезка к тому же убрала бы из разбора часть диффа без ведома клиента». Нет: «выдача большего списка нарушает правило» — это повтор правила, а не описание того, что наблюдал бы клиент.

  Техника выбрана по характеру дефекта: содержание решений в разделе верное, расходится только форма однотипных ячеек. Показать образец элемента и его антипод дешевле и точнее, чем описывать требуемую форму словами, и образец переиспользуется при добавлении новых альтернатив.

  Отклонённые кандидаты. [`tests_load.md`](../../practice_01/tests_load.md) — числа прогона разнородны по происхождению, но раздел «Происхождение чисел» уже отделяет заданные правилами величины от допущений прогона и отдельно оговаривает, что 20 RPS не выведены из 20 000 символов; образец нечего выравнивать, уместнее проверочная техника. [`problem.md`](../../practice_01/problem.md), таблица метрик — шесть строк одного вида, но все шесть уже держат форму «доля — текущее значение с цитатой — целевое — когда — источник»; неровности нет. [`tests_e2e.md`](../../practice_01/tests_e2e.md) — девять строк, у каждой заполнены все пять колонок с наблюдаемым критерием, образец не нужен.

## Примеры

### Хороший результат

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Не ограничивать `risks` тремя элементами, отдавать весь список | OUT-1 задаёт максимум три элемента в `risks`, каждый с полями `file`, `line`, `evidence`, `risk`; отправная точка — `return {"comment": answer}` (хунк `app/review_service.py @@ -1,10 +1,23 @@`), где массива `risks` нет вовсе, поэтому его длина задаётся при сборке ответа, а не наследуется. Наблюдаемый эффект отказа: на заглушке, вернувшей пять кандидатов в риски, клиент получает `len(risks)` равную 3, а не пять ([`tests_e2e.md`](tests_e2e.md), граничный сценарий). Решение окончательно, пока действует OUT-1: возврат к вопросу — только при изменении самого правила, профиль трафика и объём диффа на него не влияют |

Чем хорош: ячейка содержит все четыре элемента образца. Первый — источник запрета назван по ID (OUT-1) с формулировкой, которая берётся из [`context.md`](../../practice_01/context.md), раздел «Факты и правила». Второй — отправная точка подтверждена дословной цитатой `return {"comment": answer}` со ссылкой заголовком хунка `app/review_service.py @@ -1,10 +1,23 @@`, а не номером строки: оба файла в диффе начинаются со строки 1, поэтому номер невоспроизводим. Третий — назван наблюдаемый эффект отказа через конкретный вход (заглушка с пятью кандидатами) и наблюдаемое значение (`len(risks)` равна 3), то есть читатель может проверить последствие, а не поверить ему. Четвёртый — указано условие возврата к вопросу, причём именно то, которое следует из источника: правило меняется — решение пересматривается; посторонние условия вроде профиля трафика прямо исключены. Ни одного числа сверх заданных правилами в ячейке нет.

### Плохой результат

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Не ограничивать `risks` тремя элементами, отдавать весь список | Длинный список рисков ухудшает читаемость разбора и снижает доверие ревьюеров, поэтому стабильно отдавать весь список нецелесообразно: практика показывает, что ревьюер осиливает не больше 5–7 пунктов за проход. Ограничение в три элемента улучшает восприятие ответа и ускоряет работу с PR примерно на 30%. Проблема видна в `app/review_service.py`, строки 19–22. В дальнейшем планируется улучшить сортировку рисков по важности |

Чем плох по QA-1 (утверждение включается, только если подтверждено строкой диффа или правилом):

- «ухудшает читаемость», «снижает доверие», «улучшает восприятие» — намерение и оценка вместо наблюдаемого критерия: ни одно из этих утверждений нельзя проверить входом и наблюдаемым результатом, тогда как проверяемая формулировка существует — `len(risks)` равна 3 на заглушке с пятью кандидатами.
- «ревьюер осиливает не больше 5–7 пунктов», «ускоряет работу примерно на 30%» — числа без источника. величины, заданные правилами, перечислены в [`tests_load.md`](../../practice_01/tests_load.md), раздел «Происхождение чисел»: порог 20 000 символов и код 413 (API-1), timeout 10 секунд (REL-1), максимум три элемента `risks` и четыре обязательных поля элемента (OUT-1); ни 5–7, ни 30% не следуют ни из хунков, ни из правил, а «примерно» и «стабильно» не превращают оценку в величину.
- «`app/review_service.py`, строки 19–22» — невоспроизводимая ссылка: оба файла в `TRAINING_PR.diff` начинаются со строки 1, таких строк в диффе нет. Ссылаться следует заголовком хунка `app/review_service.py @@ -1,10 +1,23 @@`.
- Главный дефект по существу: правило OUT-1 — единственное основание отказа — не названо вообще, поэтому отказ выглядит вкусовым решением автора, хотя он обязателен. Заодно ячейка меняет смысл строки: вместо причины отказа от альтернативы она обосновывает выгоду принятого решения.
- «В дальнейшем планируется улучшить сортировку рисков по важности» — новая сущность, которой в разделе нет: сортировка `risks` относится к инкременту 3 в [`project_management.md`](../../practice_01/project_management.md) и к причине отказа отношения не имеет.

## Что получили

Агент разобрал все семь строк раздела. Обозначения частей образца: (1) источник отказа, (2) отправная точка в коде, (3) наблюдаемый эффект отказа, (4) статус решения и условие возврата.

**Строка 1 — «Оставить текущее поведение: `payload["diff"]` без проверки и `{"comment": answer}`».** Соответствует образцу частично: есть (1) — перечислены API-1, REL-1, OUT-1, SEC-1; есть (2) — цитаты `payload["diff"]` и `{"comment": answer}` в самой альтернативе; есть (3) — «Тело `{}` при этом остаётся падением на `KeyError`». Нет (4). Переписанный вид ячейки:

> Расходится сразу с четырьмя правилами: API-1 (нет проверки длины), REL-1 (нет таймаута и `try/except`), OUT-1 (одно поле вместо трёх), SEC-1 (дифф уходит дословно). Тело `{}` при этом остаётся падением на `KeyError` на строке `return review_service.review(payload["diff"])` (хунк `app/api.py @@ -1,8 +1,17 @@`). Решение окончательно: сохранение текущего поведения означает нарушение четырёх правил одновременно, поэтому возврат к вопросу возможен только при отмене этих правил.

**Строка 2 — «Отдавать все отказы одним кодом 400».** Есть (1) — API-1; есть (3) — «клиент перестаёт отличать превышение 20 000 символов от некорректного тела». Нет (2) и нет (4). Переписанный вид:

> API-1 прямо требует именно 413 для диффа длиннее 20 000 символов, поэтому единый 400 нарушает правило. Отправная точка — вывод об отсутствии: строки сравнения длины входа с порогом нет ни в одном из двух хунков, то есть код отказа задаётся при разработке с нуля. Наблюдаемый эффект отказа: на диффе 20 001 символ клиент видит 413, а на теле `{}` — 422, и по коду отличает превышение длины от некорректного тела ([`tests_e2e.md`](tests_e2e.md), граничный и негативный сценарии). Решение по 413 окончательно, пока действует API-1; коды 422, 502 и 503 остаются проектным решением этой работы и пересматриваются при появлении правила о кодах ответа.

**Строка 3 — «Обрезать дифф до 20 000 символов вместо отклонения».** Есть (1) — API-1; есть (3) — «молчаливая обрезка убрала бы из разбора часть диффа без ведома клиента». Нет (2) и нет (4). Переписанный вид:

> API-1 задаёт отклонение с HTTP 413, а не усечение. Отправная точка — вывод об отсутствии: строки, ограничивающей размер входа, нет ни в одном хунке, дифф целиком уходит в промпт на строке `prompt = f"Review this pull request and find problems:\n{diff}"` (хунк `app/review_service.py @@ -1,10 +1,23 @@`). Наблюдаемый эффект отказа: на диффе 20 001 символ счётчик вызовов заглушки LLM равен нулю, то есть усечённый вход до модели не доходит вовсе ([`tests_e2e.md`](tests_e2e.md), граничный сценарий). Решение окончательно, пока действует API-1: молчаливое усечение к тому же скрыло бы от клиента, что разобрана лишь часть диффа.

**Строка 4 — «Асинхронный обработчик и очередь фоновых задач вместо синхронного `def create_review`».** Соответствует образцу полностью: есть (1) — перечень всех семи ID с указанием, что ни одно не требует смены модели исполнения; есть (2) — цитата `def create_review` в самой альтернативе; есть (3) — таймаут 10 секунд по REL-1 ограничивает удержание потока сверху; есть (4) — «Возврат к вопросу — при появлении подтверждённого профиля трафика (сейчас его нет, см. [`tests_load.md`](tests_load.md))». Это одна из двух строк-образцов раздела, переписывать не требуется.

**Строка 5 — «Не ограничивать `risks` тремя элементами, отдавать весь список».** Есть только (1) — OUT-1. Нет (2), (3), (4); вторая половина ячейки «выдача большего списка нарушает правило» повторяет первую. Самая слабая строка раздела, именно на ней построены примеры выше. Переписанный вид — образцовая ячейка из раздела «Хороший результат».

**Строка 6 — «Логировать дифф и ответ модели для разбора инцидентов».** Есть (1) — OBS-1 и дополнительно SEC-1; есть зачаток (3) — «секреты из диффа попали бы в лог». Нет (2) и нет (4). Переписанный вид:

> Прямо запрещено OBS-1: в лог пишутся только `request_id`, длительность и статус. Отправная точка — вывод об отсутствии: строк логирования нет ни в одном из двух хунков, поэтому состав записи задаётся с нуля и соблюдение правила сейчас подтвердить нечем.
