# Промты Практики 2: шесть техник над одним артефактом

## 1. Few-shot

```text
[общая шапка]

Ниже — хороший и плохой пример строки нагрузочного сценария для
practices/practice_01/tests_load.md.

ХОРОШИЙ ПРИМЕР:
| L-3 | Деградация провайдера: медленные ответы | 10 RPS, 3 минуты; заглушка
LLM отвечает через 11 секунд | 100% ответов — 503; P95 ≤ 11 с | P95 и максимум
времени ответа, доля 503 | REL-1 задаёт timeout 10 секунд, отсюда предел 11 с
как «таймаут плюс секунда на обвязку»; вызов `self.llm.generate(prompt)`
в хунке `app/review_service.py @@ -1,10 +1,23 @@` сделан без таймаута |
Чем хорош: предел 11 с выведен из числа 10, которое есть в REL-1; заглушка
на 11 секунд подобрана так, чтобы таймаут гарантированно сработал; в evidence
и правило, и строка диффа; измеряемая величина названа (P95, доля 503).

ПЛОХОЙ ПРИМЕР:
| L-9 | Пиковая нагрузка | 500 RPS, 10 минут | Сервис стабилен, P95 в норме,
ошибок мало | Стабильность | Нагрузочное тестирование — стандартная практика |
Чем плох: 500 RPS и 10 минут не выведены ни из правила, ни из диффа —
целевого профиля трафика в источниках нет; «стабилен», «в норме», «мало»
не наблюдаемы, порога отказа нет; в evidence вместо правила общая фраза.

Задача: разбери по этому образцу четыре существующих сценария L-1…L-4
в tests_load.md. Для каждого укажи:
1) какие числа выведены из источника и из какого именно;
2) какие числа назначены без источника;
3) переписанную строку evidence, в которой происхождение каждого числа видно
   прямо в строке, а назначенное число помечено как допущение с условием,
   при котором оно будет заменено.
Не добавляй новых сценариев. Если для числа источника нет и придумать
его нечестно — так и напиши.
```

## 2. R.C.T.F.

```text
[общая шапка]

Проверяемый черновик — четыре утверждения из tests_load.md:
A. «P95 ≤ 2,5 с при задержке заглушки 2 с, то есть накладные расходы обвязки
   не больше 0,5 с — 25% от задержки провайдера».
B. «100% диффов на 19 999 и 20 000 символов приняты» (сценарий L-2).
C. «P95 времени ответа ≤ 11 с... ни один запрос не висит дольше 15 с»
   (сценарий L-3).
D. «Порядок прогона фиксирован: L-1 → L-2 и L-3 → L-4».

Шаг 1. Составь по 2–3 проверочных вопроса к каждому утверждению.
Вопросы должны быть такими, чтобы ответ на них находился в разрешённых
источниках, а не в общих знаниях о нагрузочном тестировании.
Примеры формы вопроса: «какое правило называет это число?»,
«какая строка диффа это подтверждает?», «что произойдёт с утверждением,
если источник числа отсутствует?».

Шаг 2. Ответь на каждый вопрос, приведя evidence: ID правила или цитату
из хунка. Если ответа в источниках нет — напиши «не подтверждено».

Шаг 3. По результатам проверки выдай исправленные формулировки A–D.
Утверждение, не прошедшее проверку, не удаляй молча: переформулируй его
так, чтобы оно стало честным (например, из «предел» в «допущение прогона,
заменяется после L-1»).

Шаг 4. Отдельным списком — что осталось непроверяемым и почему.
Скрытые рассуждения не выводи: нужны только вопросы, evidence и результат.
```

## 4. Tree of Thoughts

```text
[общая шапка]

Решение, для которого нужны альтернативы: в tests_load.md нет целевого
профиля трафика, поэтому числа 10 RPS и 20 RPS ничем не обоснованы.
Нужно решить, что поставить на место отсутствующего профиля.

Критерии выбора, по которым оценивается каждая альтернатива:
1) проверяемость: можно ли по QA-1 показать источник каждого числа;
2) воспроизводимость: сможет ли другой инженер повторить прогон
   без устных пояснений;
3) связность с adr.md: становится ли проверяемым условие возврата
   к асинхронной очереди;
4) честность: не выдаётся ли допущение за факт.

Предложи ровно три альтернативы. Каждую опиши снаружи — что именно
записано в файле и что делает инженер, читающий его, — без описания
своего хода рассуждений. Для каждой альтернативы дай плюсы, минусы
и оценку по всем четырём критериям.

Рассмотри в том числе: (а) оставить назначенные числа с явной пометкой
«допущение первого прогона»; (б) перейти от абсолютного RPS к профилю,
выведенному из ограничений REL-1 и API-1 (например, нагрузка задаётся
числом параллельных запросов относительно числа воркеров, а не RPS);
(в) сделать первый прогон калибровочным — он не проверяет порог,
а измеряет его, и только второй прогон проверяет.

Затем выбери одну и укажи: почему именно она, что изменится в tests_load.md
и как проверить, что выбор сработал. Отклонённые альтернативы не удаляй —
их формулировки пойдут в файл эксперимента.
```

## 5. RAG

```text
[общая шапка]

Вопрос к источникам: какие числовые пороги нагрузочного прогона можно
вывести из разрешённых источников, а какие в них отсутствуют?

Разрешённый набор фрагментов — только эти пять, ничего больше:
1. CASE.md, «Правила репозитория», API-1: «diff длиннее 20 000 символов
   отклоняется с HTTP 413».
2. CASE.md, «Правила репозитория», REL-1: «внешний LLM-вызов имеет
   timeout 10 секунд; ошибка превращается в контролируемый ответ».
3. CASE.md, «Правила репозитория», OUT-1: «в risks максимум три элемента».
4. TRAINING_PR.diff, хунк `app/api.py @@ -1,8 +1,17 @@`:
   `def create_review(payload: dict) -> dict[str, str]:` — объявление
   синхронного обработчика.
5. TRAINING_PR.diff, хунк `app/review_service.py @@ -1,10 +1,23 @@`:
   `answer = self.llm.generate(prompt)` — вызов без таймаута.

Задача:
1) Выпиши каждый порог, который выводится из этих фрагментов, с прямой
   ссылкой на номер фрагмента и с указанием, как именно он выводится.
2) Отдельным списком — пороги, присутствующие сейчас в tests_load.md,
   которые ни из одного фрагмента не выводятся.
3) Для каждого невыводимого порога укажи, какого источника не хватает
   (например: «целевой профиль трафика; в пяти фрагментах его нет»).
4) Не достраивай недостающее из общих знаний о нагрузочном тестировании.
   Ответ «в разрешённых источниках этого нет» — допустимый и ожидаемый.

Формат: три списка по пунктам выше плюс одна итоговая строка —
сколько порогов файла выводимы и сколько нет.
```

## 6. ReAct

```text
[общая шапка]

Цель: найти в tests_load.md все числа, у которых нет источника,
и для каждого зафиксировать наблюдение, подтверждающее отсутствие.

Доступные входы: пять файлов из общей шапки.

Разрешённые действия (других нет):
- READ <файл> <раздел> — прочитать конкретный раздел;
- GREP <строка> <файл> — найти вхождение числа или правила;
- COMPARE <число в tests_load.md> <источник> — сопоставить.

Запрещено: открывать файлы вне списка, обращаться к интернету, запускать
код, предлагать правки в app/, изменять файлы Практики 1 в ходе шагов.

Максимум шагов: 8.

Условие остановки: остановиться раньше восьмого шага, если все числа
из таблицы L-1…L-4 уже сопоставлены с источником или помечены как
неподтверждённые. Остановиться и задать вопрос человеку, если
обнаружится противоречие между двумя источниками (например, число
в tests_load.md противоречит числу в adr.md или problem.md) —
разрешать противоречие самостоятельно нельзя (SCOPE-1).

Формат ответа — таблица шагов:
| Шаг | Действие | Наблюдение | Продолжить или остановиться |
После таблицы — итог: список чисел без источника и причина остановки
(исчерпан лимит шагов / все числа сопоставлены / найдено противоречие).
Скрытые рассуждения между шагами не выводи — только действие и наблюдение.
```
